# Execute Application Analysis as a durable asynchronous job

Running several thinking-enabled analyses and their bounded recovery calls can outlive a reliable browser request, while spend reservations and completed work must survive disconnects and service restarts. The Run Analysis action therefore creates a durable Analysis Run and returns its identity without waiting for the requested work to finish; a background worker advances the run, and clients observe its persisted progress and terminal outcome. An Applications-owned local SQLite store persists only coordination metadata such as identifiers, status, counters, leases, attempts, cost reservations, and the ordered IDs in the Run Candidate Set; it never stores Job Content, Master Resume evidence, prompts, reasoning, provider payloads, or generated analysis. Notion remains the authoritative product record for Applications and completed analyses. A run moves through `queued`, `running`, optional `cancelling`, and `finished`; a finished run records exactly one Analysis Run Outcome of `target_met`, `spend_limited`, `attempt_budget_exhausted`, `queue_exhausted`, `cancelled`, `authorization_blocked`, or `failed`, with `failed` reserved for a Run-Scoped Failure rather than ordinary Candidate-Scoped Failures. Only one Analysis Run may be active at a time, and that run has only one provider call in flight; sequential execution continues across Applications until a stopping condition is reached, so batching does not require parallel calls. Repeating a start with the same client-generated idempotency key returns the existing run, while a distinct start during an active run neither queues nor mutates work and instead identifies the active run for the client to follow. On backend startup, the worker automatically reclaims queued runs and runs with expired leases, reconciles or conservatively consumes previously sent calls, and reauthorizes every new call; a run that no longer passes authorization finishes as `authorization_blocked`, while cancelled and finished runs never resume. Provider-call reservations are persisted before sending; an unreconciled sent call becomes an Indeterminate Attempt whose reservation remains consumed, and only a separately authorized fresh call may retry it. Cancelling a run prevents new calls but does not assume an in-flight call can be stopped or refunded: a valid in-flight result is committed and counted, an unreconciled one follows the indeterminate policy, and all earlier completions remain committed. The durable run is the coordination boundary for target progress, attempts, cost authorization, and recovery, while each completed Application remains committed independently.
