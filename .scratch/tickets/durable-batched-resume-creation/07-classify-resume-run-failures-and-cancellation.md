# Classify Resume Run failures, outcomes, and cancellation

Parent: [Wayfinder: Durable Batched Resume Creation](map.md)

Type: grilling

Status: ready-for-agent

State: closed

Assignee: codex

Blocked by: [Prototype the minimal Resume Run durability boundary](06-prototype-resume-run-durability-boundary.md)

## Question

Which revalidation, evidence, provider, spend, storage, and artifact conditions are Candidate-Scoped versus Run-Scoped; which safe candidate states, terminal Resume Run outcomes, reason codes, and stopping precedence represent them; and what exactly happens when cancellation arrives during revalidation, either model stage, PDF staging, or each artifact mutation?

The decision should cover backfill, insufficient evidence, oversized or changed source, exhausted structured-output recovery, authentication and balance defects, rate limits and provider outages, indeterminate calls, independently existing Resumes, incomplete cleanup, valid in-flight work, preservation of earlier Resume Completions, and the prohibition on starting another provider call after cancellation.

## Decisions

- Resume Artifact Quarantine is orthogonal to failure scope. Merida classifies the condition that caused quarantine rather than treating quarantine itself as a candidate or run outcome: a definitive defect isolated to one candidate ends that candidate and permits bounded backfill once no automatic mutation for it remains in progress, while a shared authority or infrastructure defect stops the Resume Run. In either case, the Application-scoped quarantine survives independently until its evidence-backed exit.
- Cancellation is a forward-only scheduling barrier, not rollback. Once cancellation is recorded, Merida starts no Resume Candidate Admission or provider call and preserves every earlier Resume Completion and all honest spend evidence. An in-flight Requirements call may settle, but even a valid result cannot authorize the prohibited Draft call; a valid in-flight Draft or an already-started Resume Artifact Set instead continues through Same-Run Artifact Recovery to a Resume Completion when safe. Definite source conflict still triggers strict compensation of unambiguous run-owned effects, and uncertain ownership, effect, or cleanup still enters Resume Artifact Quarantine; cancellation never weakens those safeguards.
- Durable transaction order resolves every cancellation race. If cancellation commits before a provider call's may-have-dispatched marker, that transmission is forbidden; affirmative non-dispatch releases its reservation but never restores the consumed stage attempt. If the marker commits first, the call remains in flight and is reconciled honestly despite cancellation. A valid marked Draft may still atomically establish its Resume Artifact Set and checkpoint for forward recovery, while lease fencing prevents the losing stale worker from dispatching or writing later state.
- Exhausted recovery for rate limiting, provider-server errors, or transport unavailability is Run-Scoped. After both attempts available to the current stage have been consumed without a usable result, the run starts no later candidate because it would exercise the same shared provider path and risk predictably repeating the defect. The current candidate retains the specific safe failure reason and all earlier Resume Completions remain intact.
- Exhausted structured-output recovery is Candidate-Scoped. Two empty, truncated, malformed, or semantically invalid Requirements or Draft responses end that candidate, retire any pre-artifact private checkpoint from which recovery is no longer permitted, and allow bounded backfill. Evidence of a shared request-protocol, model-approval, or adapter defect is classified separately as Run-Scoped rather than hidden behind this candidate-output classification.
- An exact rendered request whose Resume Input Cost Bound plus stage output allowance exceeds the approved model context is a pre-transmission Candidate-Scoped Failure. Merida neither truncates the source nor transmits the call, and bounded backfill may continue. A request that fits the context but whose full Resume Call Reservation exceeds the run's remaining authorization is instead the already-defined run-stopping Spend-Limited Resume Run outcome.
- Authentication, insufficient provider balance, unavailable or stale model/pricing approval, unavailable spend authority, Resume Generation Envelope mismatch, and provider rejection of a request that already passed Merida's local context and protocol checks are immediate Run-Scoped conditions with no provider retry. They indicate shared authorization or contract defects that later candidates cannot safely escape; the specific safe condition remains distinguishable for the later outcome and reason-code taxonomy.
- An ambiguous or moving workspace observation is initially a nonterminal recovery condition, not evidence of candidate invalidation. After bounded safe-read recovery cannot establish one Stable Resume Source Observation, the condition is Run-Scoped: the run performs no provider or artifact action, does not advance to another candidate, and preserves earlier work under a safe workspace-observation reason. Elapsed time alone never converts ambiguity into definite disappearance, change, or cleanup authority; ambiguity after an artifact effect follows Resume Artifact Quarantine instead.
- Stable Resume Source Observation permits at most three logical observation attempts and accepts the first pair of consecutive complete attempts with identical Resume Source Version Proof. Starting an observation consumes one slot even when a constituent read or pagination step fails. Each logical attempt has one outer 300-second monotonic absolute deadline that includes all constituent requests, pagination, recursion, and their transport retries; it is enforced around the entire attempt rather than checked only between requests. Every constituent retry-safe Notion request retains the transport's existing maximum of three attempts. An incomplete attempt, exhausted outer deadline, cursor cycle, or supported content/depth/response bound breaks consecutiveness. Three complete but nonmatching attempts produce `workspace_observation_unstable`; exhaustion with any incomplete attempt produces `workspace_unavailable`, unless an earlier consecutive complete pair already succeeded. During pre-Artifact admission or provider-continuation observation, cancellation may let the currently executing retry-safe request return, but it starts no next retry, constituent request, pagination request, or logical observation, and the returned evidence cannot authorize admission or provider work. Once a Resume Artifact Set exists, cancellation still permits the fenced source observations, Artifact Set reconciliation and readback, Resume Completion Gates, and compensation verification required for safe drain; those reads cannot authorize a new candidate or provider call.
- After an ambiguous Resume or Note creation, Merida performs exactly one immediate bounded reconciliation pass using the exact Resume Artifact Set ID and complete content, property, relation, and cardinality validation. One uniquely valid keyed page is preserved and Same-Run Artifact Recovery continues; zero matches, multiple matches, or any mismatch enters Resume Artifact Quarantine and never triggers an automatic resend. When the underlying defect is isolated to that candidate, automatic mutation stops and bounded backfill may continue; the candidate remains `recovering` if later evidence could still prove a valid completion, while a definitive compensation-only disposition follows the terminal-failure rule.
- Every Notion, PDF, or compensation mutation uses exactly one external mutation per durable effect attempt and at most two durable attempts for that canonical effect across uninterrupted execution and restart. Hidden transport retries are disabled for page creation, PDF publication metadata, Note creation, relation attachment, archival, relation clearing, and every other write. A second attempt is allowed only after affirmative non-dispatch or, for an idempotently repeatable effect, fresh observation proves the desired state absent while every prerequisite still holds. Ambiguous Resume or Note creation never receives an automatic second transmission. After the final attempt, fresh reconciliation either proves the desired state and advances, proves an isolated definitive conflict and enters compensation, records uncertainty in Resume Artifact Quarantine, or records the demonstrated shared authority/infrastructure defect as Run-Scoped. Unavailable reconciliation both quarantines any unproved artifact effect and stops the run when the read defect is shared.
- PDF rendering and local-storage defects are scoped by demonstrated blast radius rather than subsystem. A deterministic rendering rejection confined to one candidate's validated document, or an isolated Artifact Set identity or digest conflict, is Candidate-Scoped and uses quarantine wherever ownership is uncertain before bounded backfill. A shared renderer/library failure uses `artifact_rendering_unavailable`; disk capacity, permissions, unavailable shared PDF index, or another storage-authority defect uses `artifact_storage_unavailable`. An unclassified storage or execution defect defaults to Run-Scoped until evidence proves candidate isolation.
- Protected-checkpoint defects are scoped by dependency and proven blast radius. An unavailable or corrupt Master Source Checkpoint, missing checkpoint-key authority, or unavailable Resume Run transaction store is Run-Scoped. An isolated corrupt Draft Basis Checkpoint before artifact effects is Candidate-Scoped and ends that candidate without replaying Requirements; an isolated corrupt Resume Artifact Checkpoint after effects begin ends the candidate in Resume Artifact Quarantine. Backfill may continue only after no automatic mutation for the isolated candidate remains active, and any checkpoint defect not proven isolated defaults to Run-Scoped.
- Once a candidate is definitively unable to complete after its Resume Artifact Set exists, strict verified compensation is mandatory before that candidate becomes terminal and backfill begins whenever every run-owned effect and relation is unambiguously identifiable. A deterministic PDF render rejection follows a zero-effect form of the same rule: Merida verifies that no owned staged/published file, page, relation, or lookup entry exists, marks the Artifact Set terminally compensated, retires its checkpoint, and records `pdf_render_rejected`. Any uncertain ownership, effect, or cleanup result enters Resume Artifact Quarantine instead. Interruption and cancellation alone do not make completion impossible and therefore retain the forward-recovery policy.
- Resume Candidate State is independent of provider-call accounting and Resume Artifact Set disposition. Its safe values are `pending`, `evaluating`, `recovering`, `compensating`, `completed`, `skipped`, `failed`, and `cancelled`; `skipped` is reserved for a pre-provider, pre-artifact candidate rejection by either the quarantine guard or Resume Candidate Admission. Resume Artifact Quarantine and Indeterminate Resume Call remain separate axes, so a terminal `failed` or `cancelled` candidate may coexist with artifacts under quarantine or indeterminate spend evidence.
- A finished Resume Run has exactly one Resume Run Outcome: `target_met`, `spend_limited`, `attempt_budget_exhausted`, `queue_exhausted`, `cancelled`, `authorization_blocked`, or `failed`. Resume Artifact Quarantine is reported independently rather than becoming another outcome, and stable reason codes provide the specific cause. `failed` is reserved for a Run-Scoped Failure and is never produced solely by ordinary Candidate-Scoped Failures.
- The first durable transaction resolves a cancellation race with the target-reaching Resume Completion seal. A seal that atomically records the target-reaching Completion and `target_met` first makes a later cancellation a no-op; cancellation recorded first makes the eventual outcome `cancelled` even if already-started forward artifact recovery later seals enough work to equal the target. The final snapshot still reports the true Completion count, so a Cancelled Resume Run may numerically meet its Resume Batch Target.
- More generally, the first durable run-stopping decision wins across `target_met`, `spend_limited`, `attempt_budget_exhausted`, `queue_exhausted`, `cancelled`, `authorization_blocked`, and `failed`. A later cancellation request or newly observed defect cannot rewrite that decision while safe drain is in progress; it returns the current run. Conversely, a cancellation decision committed first retains `cancelled` through every later drain observation. The lifecycle becomes `finished` only at the safe drain boundary, but the winning outcome and reason are immutable from their deciding transaction.
- Other stopping precedence favors the specific condition that prevented safe work over incidental exhaustion. A committed cancellation wins over defects discovered later while draining already-started work; authorization and readiness are validated before spend admission, so `authorization_blocked` wins when authority is invalid and `spend_limited` requires an otherwise valid exact reservation. A Run-Scoped Failure encountered during evaluation wins over later Resume Candidate Set exhaustion, while `attempt_budget_exhausted` or `queue_exhausted` applies only when no earlier stopping condition exists.
- Resume Candidate Admission's remote Stable Resume Source Observation precedes its atomic disposition transaction. Cancellation committed before that transaction leaves the candidate `pending` and consumes no evaluation; the read may return but cannot authorize admission. If successful admission commits first, it atomically binds the Resume Source Version Proof, consumes the evaluation, and makes the candidate `evaluating`; a definite Admission rejection instead atomically consumes the evaluation and makes it `skipped`. Cancellation before any subsequent call crosses its may-have-dispatched marker makes the admitted `evaluating` candidate `cancelled` with `operator_cancelled`. Affirmative non-dispatch releases an existing reservation without restoring its consumed stage attempt, and untouched Resume Candidate Set entries remain `pending`.
- Cancellation during an in-flight Requirements call always records and settles trustworthy billing evidence but never permits Draft generation. A Draft Basis Checkpoint committed before cancellation is retired when the candidate becomes `cancelled`; when cancellation commits first, the later result creates no private Draft Basis and retains only safe call-accounting evidence. Every Requirements result, including a valid response and an Indeterminate Resume Call, converges on the same `cancelled` candidate state because no new provider call is permitted.
- Cancellation during an in-flight Draft call always reconciles billing independently. A valid Draft from a call whose may-have-dispatched marker preceded cancellation atomically replaces the Draft Basis with its Resume Artifact Set and Resume Artifact Checkpoint, then follows forward recovery; this remains allowed when usage evidence is indeterminate, with the complete reservation retained. A Draft attempt with no valid usable result starts no recovery call, makes the candidate `cancelled` with `operator_cancelled`, and retires its Draft Basis Checkpoint.
- A Resume Artifact Set under potentially sealable Resume Artifact Quarantine keeps its candidate `recovering` while the run may backfill or finish. Audited later proof seals it, changes the candidate to `completed`, and increments immutable completion history even when this exceeds the Resume Batch Target; the already-recorded Resume Run Outcome remains unchanged. A compensation-only quarantine cannot later seal and may coexist with an already `failed` or `cancelled` candidate. Exceptional overshoot is bounded by the fixed Resume Candidate Set.
- Once the Resume Artifact Set and its checkpoint exist, cancellation permits every remaining deterministic forward-recovery action with the original identity and content: PDF staging or checkpoint rerender, Resume reconciliation or creation, PDF publication, Note reconciliation or creation, relation attachment, readback, and the Completion seal. Every source, ownership, digest, lease, and Resume Completion Gate check remains mandatory. A definite conflict switches to strict compensation, uncertainty switches to Resume Artifact Quarantine, and cancellation alone never pauses or destroys the set.
- During cancellation drain, Resume Candidate State records the candidate's factual disposition rather than mirroring the run outcome. A sealed Artifact Set is `completed`; a definite conflict is `compensating` while strict reversal remains active and becomes `failed` only after verified compensation or after cleanup ambiguity is quarantined with automatic mutation stopped; a quarantine that could still seal remains `recovering`; and only a candidate whose work stops solely because cancellation forbids progress before an Artifact Set exists becomes `cancelled`. The Resume Run Outcome remains `cancelled` when its cancellation transaction won.
- Cancellation during strict compensation does not pause reversal. Every remaining verified compensation barrier stays permitted because stopping voluntarily would leave known run-owned residue. Successful compensation leaves the candidate `failed`; an ambiguous cleanup step enters compensation-only Resume Artifact Quarantine, after which the run may finish `cancelled` without waiting for audited operator resolution.
- A cancelling or Run-Scoped-failed Resume Run reaches its safe drain boundary only when no provider call remains active, no external mutation lacks either durable observed evidence or durable Resume Artifact Quarantine, and the current Resume Artifact Set is sealed, fully compensated, or under quarantine with automatic mutation stopped. Only then may the run finish and atomically release the single-active-run claim. Application-scoped Resume Artifact Quarantine may persist for later audited resolution without keeping that claim.
- Resume reason codes form one bounded lowercase `snake_case` semantic namespace. They contain no raw provider text, dynamic identity, source content, exception name, or private recovery detail and answer only why a state or outcome occurred; Resume Candidate State, Resume Run Outcome, provider-call state, and Artifact Set disposition separately express lifecycle. A code is stage-specific only when Requirements and Draft have genuinely different operator meaning.
- Run creation excludes every Application with active Resume Artifact Quarantine. If quarantine appears after the fixed snapshot, a pre-admission mutation-lock check marks that candidate `skipped` with `artifact_quarantine_active` without starting Resume Candidate Admission or consuming an evaluation; the fixed slot is not replenished. Resume Candidate Admission rejection otherwise produces `skipped` with exactly one of: `application_unavailable`, `application_not_to_apply`, `application_not_analyzed`, `match_score_missing`, `match_score_below_threshold`, `analysis_score_mismatch`, `candidate_source_incomplete`, or `independent_resume_exists`. Missing Company, Role, Job Content, or Application Analysis is consolidated as `candidate_source_incomplete`; ambiguous workspace evidence never uses a skip code.
- A Candidate-Scoped Failure produces `failed` with exactly one of: `candidate_source_unavailable`, `candidate_became_ineligible`, `candidate_source_changed`, `independent_resume_created`, `insufficient_resume_evidence`, `requirements_context_exceeded`, `draft_context_exceeded`, `requirements_output_exhausted`, `draft_output_exhausted`, `draft_basis_checkpoint_unavailable`, or `pdf_render_rejected`. After an Artifact Set exists, the candidate first passes through `compensating` and retains that definitive cause until verified terminal compensation; an artifact-originated definitive cause may instead use the applicable compact `artifact_*` code. These codes distinguish source, evidence, stage envelope, protected candidate state, and deterministic document rendering without embedding source content or implementation exceptions.
- Resume Artifact Quarantine uses exactly one of the compact semantic reasons `artifact_checkpoint_unavailable`, `artifact_ownership_unproven`, `artifact_content_mismatch`, `artifact_relation_unproven`, `artifact_result_unreconstructable`, or `artifact_compensation_unproven`. The separate Artifact Set effect and disposition identify where recovery stopped, so the reason namespace does not multiply by Resume, PDF, Note, and attachment stages; `quarantined` itself is never a reason code.
- The `authorization_blocked` Resume Run Outcome uses exactly one of: `provider_authentication_failed`, `provider_balance_insufficient`, `rate_card_unavailable`, `pricing_approval_expired`, `model_not_approved`, `tokenizer_unavailable`, `protocol_overhead_unapproved`, `spend_authority_unavailable`, `generation_envelope_mismatch`, or `provider_pricing_anomaly`. A provider request rejected after passing Merida's local validation is a contract failure under `failed`, not an authorization reason.
- Shared provider failure under the `failed` Resume Run Outcome uses exactly one of: `provider_request_rejected`, `provider_protocol_failure`, `provider_rate_limit_exhausted`, `provider_unavailable_exhausted`, `provider_transport_exhausted`, or `provider_recovery_exhausted`. The final code is limited to two-attempt mixtures of retryable rate-limit, provider-unavailable, transport/indeterminate, and unusable-output results. Authentication, balance, request, protocol, returned-model, usage, and pricing defects are immediate and retain their specific reason rather than being folded into mixed exhaustion. Only two attempts consisting entirely of unusable structured output remain Candidate-Scoped as `requirements_output_exhausted` or `draft_output_exhausted`.
- Shared workspace, rendering, storage, and execution failure under the `failed` Resume Run Outcome uses exactly one of: `workspace_observation_unstable`, `workspace_unavailable`, `workspace_access_invalid`, `workspace_contract_mismatch`, `artifact_rendering_unavailable`, `artifact_storage_unavailable`, `checkpoint_key_unavailable`, `checkpoint_store_unavailable`, `master_checkpoint_unavailable`, `run_store_unavailable`, `storage_failure_unclassified`, or `run_execution_failure`. Malformed successful workspace payloads and locally validated mutation requests rejected for schema/contract reasons use `workspace_contract_mismatch`; exhausted timeout, network, rate-limit, or server recovery uses `workspace_unavailable`; and an unexpected invariant or worker defect with no safer mapping uses `run_execution_failure`. Candidate-isolated checkpoint and artifact defects retain their candidate or quarantine codes; these run reasons require shared impact or an unclassified blast radius.
- Reason presence follows Resume Candidate State and Resume Run Outcome. `pending`, `evaluating`, ordinary forward `recovering`, and `completed` candidates have no candidate reason; a `recovering` candidate's quarantine cause lives on its Artifact Set. `skipped`, `failed`, `cancelled`, and `compensating` require one semantic reason: cancellation uses `operator_cancelled`, compensation and terminal failure retain the definitive cause that required reversal, and a run-stopped admitted candidate uses the run's reason. Standard run outcomes use the matching reason `target_met`, `spend_limited`, `attempt_budget_exhausted`, or `queue_exhausted`; cancellation uses `operator_cancelled`; and `authorization_blocked` or `failed` requires one code from its approved set. Reasons clear only when the candidate becomes `completed`, and a recorded terminal run reason never changes during audited late recovery.
- Resume Run Lifecycle has exactly four values: `queued`, `running`, `cancelling`, and `finished`. Cancellation is idempotent; repeating it while `cancelling` returns the current run, and cancelling a `finished` run is a no-op. Candidate and Artifact Set state represents recovery, compensation, and quarantine without adding paused, recovering, or attention-required run lifecycles.
- Resume Candidate terminality is strict: `completed`, `skipped`, `failed`, and `cancelled` never reopen or receive another evaluation. `recovering` is the only state that may outlive a finished run and later become `completed` or enter `compensating`; `compensating` becomes `failed` after verified reversal or after an ambiguous cleanup is durably retained as compensation-only quarantine with automatic mutation stopped. A Resume Completion remains immutable.
- Candidate exhaustion depends only on the immutable run-start snapshot. Once every fixed candidate is terminal or is safely deferred in quarantine with no automatic mutation active, the run uses `attempt_budget_exhausted` only when the run-start eligible queue was truncated at `target × 2`; otherwise it uses `queue_exhausted`. Later queue changes and audited late completions never rewrite that outcome.
- Indeterminate Resume Call remains a call-accounting fact rather than a candidate state or outcome. Normal execution may use the one remaining stage slot only after source revalidation and fresh Resume Cost Authorization; exhausted slots use the homogeneous or mixed provider-failure rules, while cancellation forbids recovery. Trustworthy usage discovered later may settle committed spend downward but never restores an attempt, resurrects model output, changes Resume Candidate State, or rewrites a terminal Resume Run Outcome.
- Readiness failure before run creation rejects the start and creates no Resume Run, idempotency binding, Resume Candidate Set, reservation, or artifact intent. After creation, provider or spend readiness is evaluated only when another provider call is required: its loss records `authorization_blocked`, but it never prevents deterministic recovery or sealing of an existing Artifact Set. Shared workspace, artifact-storage, or checkpoint loss records `failed` after the safe drain boundary. A total run-store outage first suspends work fail closed and can record `failed` only after transactional authority recovers with durable evidence of that outage; a previously committed stopping decision retains precedence.
- Provider response fields separate output validity from billing evidence. `length`, empty content, malformed JSON, semantic invalidity, and `content_filter` consume a stage attempt as unusable structured output; two attempts consisting only of those results produce the stage's Candidate-Scoped `requirements_output_exhausted` or `draft_output_exhausted`. `insufficient_system_resource` follows provider-unavailable recovery and may exhaust as Run-Scoped `provider_unavailable_exhausted`. Missing required model or finish-reason fields and unexpected `tool_calls` when no tools were requested are immediate `provider_protocol_failure`; a returned-model contradiction is `provider_pricing_anomaly` and invalidates the output. Missing or unmatchable call/usage evidence makes billing Indeterminate without by itself invalidating otherwise usable output; contradictory usage or pricing is `provider_pricing_anomaly`, retains the conservative reservation, and stops later calls, but output remains independently subject to model, finish-reason, JSON, and semantic validation. Only `stop` with the approved returned model, valid JSON, and semantic validation completes a stage.
- Backfill follows one closed rule: Merida may advance only to the next member of the immutable Resume Candidate Set, only while the Resume Batch Target remains unmet, and only while the Resume Attempt Budget remains. Advancement is allowed after Resume Candidate Admission produces `skipped`, a Candidate-Scoped Failure produces `failed`, verified compensation finishes an isolated artifact failure, or an isolated quarantine has stopped its automatic mutations, including a potentially sealable quarantine. Advancement is forbidden after `target_met`, `spend_limited`, `cancelled`, `authorization_blocked`, or Run-Scoped `failed`; it never appends newly discovered candidates or restores a consumed evaluation.
- When a run-stopping condition occurs after Resume Candidate Admission but before a Resume Artifact Set exists, the admitted candidate becomes `failed` with the same specific semantic reason recorded for the run, including `spend_limited`, an approved authorization reason, or an approved Run-Scoped failure reason; its consumed candidate evaluation is not restored, and untouched Resume Candidate Set entries remain `pending`. Once an Artifact Set exists, its factual safe-drain disposition takes precedence: it becomes `completed`, `failed` after definite compensation, or remains `recovering` beside a potentially sealable quarantine. Exhaustion outcomes arise only after no candidate remains active and therefore relabel no candidate.
- Cancellation that commits while the run is still `queued`, before any worker claim, atomically finishes it as `cancelled` with reason `operator_cancelled`. Every candidate remains `pending`, no candidate evaluation, provider-attempt, spend, or artifact counter is consumed, and the now-unneeded Master Source Checkpoint is retired without erasing the safe run or idempotency record. If a worker's durable claim commits first, the running cancellation rules apply instead. The finished run and its idempotency binding remain queryable; cancellation never erases the audit record.
- Once a provider call's may-have-dispatched marker commits, cancellation does not actively abort the request; Merida awaits its normal bounded response or timeout. A local socket or task abort could not prove that provider execution stopped and therefore cannot establish non-dispatch. If the runtime disappears or the bounded wait ends without trustworthy evidence, the call becomes Indeterminate and retains its full reservation, while cancellation still forbids every recovery call.

## Answer

Classify a condition as Candidate-Scoped only when durable evidence proves that the defect is confined to one fixed candidate and later candidates can safely avoid it. Classify shared authority, provider, workspace, storage, protected-state, or unclassified execution defects as Run-Scoped. Treat uncertainty about an external artifact effect as Resume Artifact Quarantine rather than inventing success or failure; the demonstrated underlying scope independently decides whether the run may backfill or must stop.

Cancellation records one immutable run-stopping decision and prohibits every later Resume Candidate Admission and provider call. It is not rollback and does not weaken spend accounting, artifact ownership, Resume Completion Gates, compensation, or quarantine. Requirements-only work settles and stops, while a valid in-flight Draft or an existing Artifact Set continues deterministically toward seal, verified compensation, or quarantine. The run releases its active claim only after that bounded safe drain.

The implementation must keep run lifecycle, run outcome, candidate state, provider-call accounting, and Artifact Set disposition as separate axes. One bounded semantic reason explains each stopped run or non-completed candidate, and deterministic evaluation order selects that reason when several facts coexist.

## Problem Statement

Resume Creation crosses paid provider calls, nontransactional Notion mutations, local PDF storage, protected recovery checkpoints, and a final relation-last commit. A single generic `failed` flag cannot say whether Merida may try the next candidate, must stop the run, can continue an accepted Draft, must compensate known effects, or has too little evidence to mutate anything. Cancellation adds races at every one of those boundaries and cannot safely mean either "kill the local task" or "delete everything created so far."

The failure contract therefore needs to preserve five independent truths:

1. whether the Resume Run may still schedule work;
2. what happened to the current candidate;
3. whether a provider call was sent and how its spend is accounted;
4. which exact Artifact Set effects are proved, recoverable, compensating, or quarantined; and
5. why the relevant state or outcome was selected without exposing private content or unstable implementation errors.

## Solution

### Classification summary

| Condition | Candidate disposition | Run decision | Backfill |
| --- | --- | --- | --- |
| Start-time readiness or stable-source failure before the atomic run-creation transaction | No candidate or run exists | Reject start | Not applicable |
| Active Application quarantine found by the pre-admission lock check | `skipped` / `artifact_quarantine_active`, no evaluation consumed | Continue | Yes |
| Definite Resume Candidate Admission rejection | `skipped` with the first admission reason | Continue | Yes |
| Definite post-admission source, eligibility, evidence, context, structured-output, Draft Basis, or isolated rendering defect | `failed`, after zero-effect verification or compensation where an Artifact Set exists | Continue | Yes |
| Spend reservation does not fit an otherwise ready exact call | Admitted current candidate `failed` / `spend_limited`; no active candidate for exhaustion between candidates | `spend_limited` | No |
| Provider/spend authorization defect when another call is required | Admitted current candidate `failed` with the run reason unless an Artifact Set's drain gives a more factual disposition | `authorization_blocked` | No |
| Shared or unclassified provider, workspace, rendering, storage, checkpoint, or execution defect | Current candidate reflects safe drain and otherwise uses the run reason | `failed` | No |
| Resume Candidate Set consumed without an earlier stop | No active candidate is relabelled | `attempt_budget_exhausted` when the run-start queue was truncated at `target × 2`; otherwise `queue_exhausted` | No |
| Operator cancellation | Pre-artifact current candidate `cancelled`; an Artifact Set becomes `completed`, `failed`, or remains `recovering` according to drain | `cancelled` | No |
| Ambiguous external artifact effect or cleanup | Potentially sealable candidate remains `recovering`; compensation-only ambiguity sits beside terminal `failed` or `cancelled` | Underlying Candidate- or Run-Scoped condition decides; quarantine is not an outcome | Yes only for an isolated quarantine after automatic mutation stops |

### Candidate transitions

```text
pending -> skipped
pending -> evaluating -> failed
                      -> cancelled
                      -> recovering -> completed
                                    -> compensating -> failed
```

`pending -> evaluating` is the successful atomic Resume Candidate Admission commit that binds the Resume Source Version Proof and consumes the evaluation. A definite Admission rejection atomically produces `pending -> skipped` and consumes the evaluation; only the earlier quarantine guard may produce that transition without consuming one. A valid Draft atomically establishes the Resume Artifact Set and enters `recovering`. Terminal candidate states never reopen or receive another evaluation. A potentially sealable quarantine is the sole case in which `recovering` may outlive a finished run and later become `completed`.

### Run transitions and stopping order

```text
queued -> running -> finished
   |         |
   |         +-> cancelling -> finished
   +--------------------------> finished (queued cancellation)
```

The first transaction that records one run-stopping outcome and reason wins. It may precede the final `finished` lifecycle transition while provider settlement, artifact recovery, compensation, or quarantine reaches the safe drain boundary. Every later cancellation, target observation, exhaustion check, or defect is observational only and cannot rewrite the winning decision. A target-reaching Completion seal and `target_met` decision remain one atomic transaction.

### Deterministic reason selection

Merida evaluates gates in workflow order and records the first failing gate. Once recorded, a reason is never recomputed from later evidence. Within a gate, use these orders:

1. **Pre-admission and admission:** `artifact_quarantine_active`; `application_unavailable`; `application_not_to_apply`; `application_not_analyzed`; `match_score_missing`; `match_score_below_threshold`; `analysis_score_mismatch`; `candidate_source_incomplete`; `independent_resume_exists`.
2. **Continuation:** `candidate_source_unavailable`; `candidate_became_ineligible`; `candidate_source_changed`; `independent_resume_created`. Ambiguous evidence uses the workspace recovery contract instead of this list.
3. **Shared durable and provider authority:** evaluate `run_store_unavailable`, `checkpoint_key_unavailable`, `checkpoint_store_unavailable`, the relevant scoped checkpoint reason, `spend_authority_unavailable`, `generation_envelope_mismatch`, `rate_card_unavailable`, `pricing_approval_expired`, `model_not_approved`, `tokenizer_unavailable`, `protocol_overhead_unapproved`, `provider_authentication_failed`, then `provider_balance_insufficient`. A total physical-store outage always uses `run_store_unavailable`; narrower reasons require the earlier capabilities to remain provably available.
4. **Provider dispatch and response:** a post-dispatch authentication or balance rejection retains `provider_authentication_failed` or `provider_balance_insufficient`; rejection of a locally validated request is `provider_request_rejected`; missing required response structure or unexpected tools is `provider_protocol_failure`; returned-model mismatch is `provider_pricing_anomaly`; contradictory usage or pricing is also `provider_pricing_anomaly` for future authorization while output validation remains independent; otherwise classify finish reason and structured output. Missing matching billing evidence alone creates an Indeterminate Resume Call.
5. **Workspace observation:** an explicit access/capability rejection is `workspace_access_invalid`; a schema, malformed-success, or locally validated contract mismatch is `workspace_contract_mismatch`; bounded incomplete reads are `workspace_unavailable`; three complete nonmatching observations are `workspace_observation_unstable`.
6. **Artifact reconciliation:** inspect the canonical effect order and stop at the first failed invariant. Within one effect, use checkpoint availability, ownership/cardinality, semantic content/digest, relation proof, then result reconstruction. During strict reversal, inability to verify the current cleanup barrier uses `artifact_compensation_unproven`.
7. **Unclassified failures:** choose `storage_failure_unclassified` only for a storage-path defect with unknown blast radius; use `run_execution_failure` for any other safe caught invariant or worker failure. Raw exception types and messages never become reasons.

An HTTP or adapter label does not override demonstrated semantics. For example, definite Application absence before effects is candidate-local, while a shared 401/403 is `workspace_access_invalid`; malformed successful workspace data is `workspace_contract_mismatch`; and a lost mutation response follows effect reconciliation before scope is selected.

### Bounded recovery

- A Stable Resume Source Observation has at most three logical attempts. Each attempt and each artifact reconciliation pass has one outer 300-second monotonic absolute deadline covering its complete read graph, including pagination and recursive block reads. Each retry-safe constituent request has at most three transport attempts; a failed constituent or outer deadline consumes the logical attempt. Cursor cycles and supported content, nesting, or response-bound exhaustion fail the attempt closed. Cancellation prevents a later retry, pagination request, or logical observation from beginning when that pre-Artifact read could authorize admission or provider work. For an existing Resume Artifact Set, fenced drain-required source checks, reconciliation and readback, Resume Completion Gates, and compensation verification remain permitted, but they cannot authorize a new candidate or provider call.
- A provider stage has exactly two durable dispatch attempts under the Resume Generation Envelope. Homogeneous retryable exhaustion uses its specific provider reason, mixed retryable/unusable-output exhaustion uses `provider_recovery_exhausted`, and immediate authorization/protocol/contract defects short-circuit with their specific reason.
- Every external artifact or compensation effect has at most two durable mutation attempts, one mutation transmission per attempt, and fresh reconciliation after every ambiguous result. This is a ceiling, not permission to retry: ambiguous page creation quarantines after its one immediate reconciliation, while a second relation, PDF, or cleanup mutation requires affirmative non-dispatch or proof that an idempotently repeatable desired state is absent.
- Mutation status labels never authorize blind retry. Shared 401/403 results use `workspace_access_invalid`; a 400/409 response to a locally validated request uses `workspace_contract_mismatch` unless reconciliation proves a candidate-isolated identity conflict; a 404 involving an expected owned artifact enters identity-based reconciliation and quarantine when ownership or effect is unproved; and 429, 5xx, timeout, or network results reconcile first and use `workspace_unavailable` if their bounded shared recovery exhausts.
- After the final artifact attempt, Merida freshly observes the effect. Proven desired state advances; a definitive isolated conflict compensates; unproved ownership/effect/cleanup quarantines; and demonstrated shared workspace, rendering, storage, or authority loss also records the corresponding Run-Scoped stop.
- Retry backoff and scheduling may vary without changing these attempt counts, dispatch markers, cancellation barriers, or terminal classifications.

### Durable-store failure

The selected design uses one SQLite transaction authority, but reason codes describe the failed capability. `run_store_unavailable` means ordinary coordination transactions cannot commit; `checkpoint_store_unavailable` means coordination remains writable while checkpoint operations fail systemically; `spend_authority_unavailable` means the transaction store works but the reservation invariant cannot be enforced; and a missing or corrupt individual checkpoint follows its scoped checkpoint reason.

Merida cannot truthfully record `failed` while the run store itself is unavailable. Store loss is therefore a fail-closed suspension: the live worker stops every new external dispatch and exposes no newer or fabricated state; it may serve the last committed snapshot only when that snapshot remains safely readable or cached. If authority recovers while that fenced worker still holds direct evidence of the outage, it first reconciles any may-have-dispatched call or artifact effect and then commits `run_store_unavailable` as the stopping decision unless an earlier decision already won. If the process dies before that fact can commit, a fresh worker must not infer an unrecorded outage; after store recovery it reconciles only the last durable markers and resumes or stops from facts it can prove. If authority never recovers, the run remains durably nonterminal and retains its active claim rather than fabricating a terminal outcome.

### Checkpoint disposition

- A pre-artifact terminal candidate retires any Draft Basis Checkpoint after the terminal decision commits.
- A deterministic rendering rejection retires its Artifact Checkpoint only after zero-effect compensation proves that no owned effect exists.
- A sealed Completion or fully verified compensation makes Artifact Checkpoint deletion idempotent cleanup. Failure of that deletion never reopens or recounts the candidate.
- An isolated post-seal deletion failure may be retried while the run continues if the store still proves it can safely create and retain later checkpoints. A systemic checkpoint-store failure blocks dependent work and follows the Run-Scoped rule.
- Every potentially recoverable or compensation-only quarantine retains the checkpoint and key it needs, without time-based expiry.

## Implementation Decisions

### Ownership and module boundaries

- Keep durable coordination in the Resumes context. The Resume Run coordinator owns scheduling, failure classification, stopping decisions, cancellation, safe drain, and backfill; it consumes the previously selected Resumes-owned transaction/checkpoint store, spend policy, provider seam, workspace seam, and PDF artifact seam.
- Do not reuse the Applications-owned Analysis Run schema or treat its lifecycle and retry semantics as authority. Reuse only policy-free primitives whose interfaces preserve the Resume-specific contracts.
- Keep Notion authoritative for completed Resume and Note records, backend PDF storage authoritative for PDF bytes and lookup evidence, and the Resumes-owned transaction store authoritative for coordination, checkpoints, call accounting, stopping order, and the logical Resume Completion seal.

### Independent state axes

- Resume Run Lifecycle is exactly `queued`, `running`, `cancelling`, or `finished`.
- Resume Run Outcome is exactly `target_met`, `spend_limited`, `attempt_budget_exhausted`, `queue_exhausted`, `cancelled`, `authorization_blocked`, or `failed`.
- Resume Candidate State is exactly `pending`, `evaluating`, `recovering`, `compensating`, `completed`, `skipped`, `failed`, or `cancelled`.
- Provider-call accounting, including Indeterminate Resume Call, remains independent of output usability, Resume Candidate State, and Resume Run Outcome.
- Resume Artifact Set disposition and Resume Artifact Quarantine remain independent of candidate and run state. Quarantine is neither a failure scope nor a terminal outcome.
- Terminal candidate states never reopen or receive another evaluation. `recovering` is the only state that may outlive a finished run; it may later become `completed` or enter `compensating`. `compensating` becomes `failed` after verified reversal or after compensation uncertainty is placed under durable Resume Artifact Quarantine with automatic mutation stopped.

### Failure scope and backfill

- Classify a condition as Candidate-Scoped only when durable evidence proves it is confined to one candidate and later candidates can safely avoid it. Shared provider, workspace, rendering, storage, protected-state, or execution defects are Run-Scoped. Unknown blast radius defaults to Run-Scoped.
- A Candidate-Scoped Failure may backfill only after any required recovery or verified compensation reaches a safe boundary and no automatic mutation remains active. A Run-Scoped Failure prohibits every later candidate and preserves all earlier Resume Completions.
- Backfill selects only the next identity in the immutable Resume Candidate Set, only while the Resume Batch Target is unmet and the Resume Attempt Budget remains. It never appends a live-queue identity, restores a consumed evaluation, or reevaluates a terminal candidate.
- Backfill is allowed after a pre-provider `skipped` candidate, a Candidate-Scoped `failed` candidate, verified compensation of an isolated artifact failure, or an isolated quarantine whose automatic mutation has stopped. It is forbidden after `target_met`, `spend_limited`, `cancelled`, `authorization_blocked`, or Run-Scoped `failed`.
- Candidate exhaustion is derived from the immutable run-start snapshot. Use `attempt_budget_exhausted` only when the eligible queue was truncated at `target × 2`; otherwise use `queue_exhausted`. Later queue changes and audited late Completions cannot rewrite that decision.

### Start and Resume Candidate Admission

- Reject a start-time readiness failure, inability to establish the Master Resume Version through a Stable Resume Source Observation, or transaction-authority failure before creating a Resume Run, idempotency binding, Resume Candidate Set, reservation, or artifact intent.
- Exclude Applications under active Resume Artifact Quarantine when constructing the Resume Candidate Set.
- Recheck the quarantine mutation lock before Resume Candidate Admission. Quarantine that appeared after the snapshot produces `skipped` with `artifact_quarantine_active`, consumes no evaluation, and does not replenish the fixed slot.
- Perform the remote Stable Resume Source Observation before the atomic admission disposition. Cancellation that wins before that transaction leaves the candidate `pending`; a definite Admission rejection atomically consumes the evaluation and records `skipped`; successful Admission atomically consumes the evaluation, binds the Resume Source Version Proof, and records `evaluating`.
- Ambiguous Admission or continuation evidence enters bounded workspace recovery. It never becomes a skip, definite disappearance, definite change, or permission to advance merely because time passes.

### Provider and spend classification

- Preserve the accepted Resume Generation Envelope: Requirements uses DeepSeek V4 Flash with high-effort thinking and an 8,000-token reasoning-inclusive output ceiling; Draft uses DeepSeek V4 Pro with high-effort thinking and a 16,000-token reasoning-inclusive output ceiling; each stage has exactly two durable dispatch attempts, fixed deadlines, no fallback, no nested retry, and no restored attempt.
- A proven-unsent attempt may release its reservation but remains consumed. A may-have-dispatched call without trustworthy matching billing evidence becomes an Indeterminate Resume Call and retains its complete reservation.
- Treat billing evidence and output usability as independent reducers. Missing or unmatchable billing evidence alone does not invalidate otherwise usable output. Contradictory usage or pricing retains conservative spend and blocks later calls as `provider_pricing_anomaly`, while output is still judged independently. A returned-model contradiction invalidates output.
- Only `stop` with the approved returned model, valid JSON, and semantic validation completes a provider stage. `length`, `content_filter`, empty content, malformed JSON, and semantic invalidity consume an attempt as unusable output.
- Two attempts consisting entirely of unusable Requirements or Draft output are Candidate-Scoped. Homogeneous retryable rate-limit, provider-unavailable, or transport exhaustion is Run-Scoped with its specific reason. A two-attempt mixture of retryable shared-provider defects and unusable output uses `provider_recovery_exhausted`.
- Authentication, balance, locally valid request rejection, protocol defects, returned-model contradiction, pricing anomaly, unavailable approvals, generation-envelope mismatch, and spend-authority loss short-circuit with their specific reason and no retry.
- Reject an exact request that exceeds model context before transmission as the stage-specific Candidate-Scoped context reason. If the request fits but its complete reservation does not fit an otherwise valid remaining authorization, stop as `spend_limited`.
- Check provider and spend readiness before run creation and immediately before any call that could be authorized. Provider authority is not required to recover, compensate, quarantine, or seal an existing Resume Artifact Set.

### Stable workspace observation

- Permit at most three logical Stable Resume Source Observation attempts and accept the first consecutive pair of complete observations with identical Resume Source Version Proof.
- Starting an observation consumes one logical attempt. An incomplete attempt, cursor cycle, supported content/depth/response-bound violation, or outer deadline breaks consecutiveness.
- Give each logical observation and artifact-reconciliation pass one 300-second monotonic outer deadline covering its complete read graph, pagination, recursion, and transport retries. Each retry-safe constituent request retains at most three transport attempts.
- Use `workspace_observation_unstable` after three complete nonmatching observations. Use `workspace_unavailable` when exhausted recovery contains an incomplete observation and no earlier consecutive pair succeeded.
- During pre-Artifact admission or provider-continuation observation, cancellation may let the currently executing retry-safe request return, but no later retry, constituent request, pagination request, or logical observation may begin or authorize admission or provider work.
- Once a Resume Artifact Set exists, permit the fenced source observations, Artifact Set reconciliation and readback, Resume Completion Gates, and compensation verification required for safe drain after cancellation. These reads remain bounded and cannot authorize a new candidate or provider call.
- Before artifact effects, exhausted ambiguity is Run-Scoped and cannot advance to another candidate. After an artifact effect, unproved state enters Resume Artifact Quarantine; a demonstrated shared read defect also stops the run.

### Artifact mutation, compensation, and quarantine

- Give each canonical Notion, PDF, relation, or compensation effect at most two durable mutation attempts across uninterrupted execution and restart, with at most one external mutation transmission per attempt.
- Disable hidden write retries beneath a durable effect attempt. Retry-safe reads retain their bounded transport retry behavior.
- Permit a second mutation attempt only after affirmative non-dispatch or fresh proof that an idempotently repeatable desired state is absent and every prerequisite still holds. An ambiguous Resume or Note creation receives one immediate exact-ID reconciliation pass and no automatic resend.
- Reconcile every ambiguous effect by exact Resume Artifact Set ID and complete ownership, content, relation, digest, cardinality, and result evidence. Proven desired state advances; a definitive isolated conflict enters strict compensation; unproved ownership, effect, or cleanup enters Resume Artifact Quarantine; a demonstrated shared authority or infrastructure defect also stops the run.
- Preserve the accepted forward-only Resume Artifact Set contract: canonical effect order, same Resume Artifact Set ID and checkpoint, no provider regeneration, no replacement identity, no adoption of independent artifacts, relation-last Resume Completion Gate, and atomic Resume Completion seal.
- Once a Resume Artifact Set exists, a definitive condition that makes completion impossible must strictly compensate exactly owned effects before the candidate becomes terminal when ownership is unambiguous. Uncertain ownership, effect, relation, content, result reconstruction, or cleanup quarantines instead.
- Treat deterministic PDF rendering rejection as zero-effect compensation: prove no owned staged or published file, page, relation, or lookup entry exists; mark the Artifact Set terminally compensated; retire the checkpoint; then record `pdf_render_rejected`.
- Keep a candidate whose Resume Artifact Set is under potentially sealable Resume Artifact Quarantine `recovering`. Compensation-only quarantine may coexist with terminal `failed` or `cancelled` and cannot later seal.
- Permit audited later proof to seal a Resume Artifact Set under potentially sealable Resume Artifact Quarantine after its owning run finishes. Record the true immutable Resume Completion even when it reaches or exceeds the Resume Batch Target, retain the already-recorded Resume Run Outcome and reason, and bound all overshoot by the fixed Resume Candidate Set.

### Cancellation, stopping order, and safe drain

- Model cancellation as a forward-only scheduling barrier, not rollback. It prohibits every later Resume Candidate Admission and provider call while preserving prior Resume Completions, spend evidence, call uncertainty, Resume Artifact Set identity, checkpoints, and quarantine.
- Resolve every race by durable transaction order. The first committed run-stopping Outcome and reason wins across target, spend limitation, exhaustion, cancellation, authorization block, and Run-Scoped failure. Store that decision separately from the later transition to `finished`; no later observation may rewrite it.
- Commit the target-reaching Resume Completion seal and `target_met` decision atomically. Check authority before spend fit, so `authorization_blocked` precedes `spend_limited`; a Run-Scoped failure encountered during evaluation precedes incidental exhaustion.
- Queued cancellation atomically finishes as `cancelled` with `operator_cancelled`, leaves all candidates `pending`, consumes no evaluation, provider attempt, spend, or artifact counter, retires the unused Master Source Checkpoint, and preserves the run and idempotency audit record.
- Cancellation before successful Admission commit leaves the candidate `pending`. Cancellation after Admission but before any later provider call's may-have-dispatched marker makes the current candidate `cancelled` with `operator_cancelled`. When a marker committed first, settle that call honestly: the candidate remains `cancelled` if no usable marked Draft can establish a Resume Artifact Set, while a usable marked Draft enters forward recovery under the rule below.
- Do not actively abort a provider request after its may-have-dispatched marker. Await its normal bounded response or timeout; missing trustworthy evidence produces an Indeterminate Resume Call, and cancellation forbids a recovery call.
- During Requirements, settle trustworthy billing but never create a new Draft Basis or authorize Draft after cancellation. During Draft, a valid result whose marker won may atomically create the Resume Artifact Set and checkpoint even with Indeterminate billing; an unusable result starts no recovery call and retires the Draft Basis.
- Once a Resume Artifact Set exists, cancellation permits deterministic PDF staging or checkpoint rerender, Resume reconciliation or creation, PDF publication, Note reconciliation or creation, relation attachment, readback, Completion sealing, and required strict compensation. All source, ownership, digest, lease, and Resume Completion Gate checks remain mandatory.
- During drain, record the candidate's factual disposition: `completed` after seal, `compensating` during reversal then `failed`, `recovering` beside potentially sealable quarantine, or `cancelled` when only the scheduling barrier stopped pre-artifact work.
- Reach safe drain only when no provider call remains locally active, every started external mutation has durable evidence or durable Resume Artifact Quarantine, and the current Artifact Set is sealed, fully compensated, or under quarantine with automatic mutation stopped. Only then commit `finished` and release the single-active-Resume-Run claim atomically.

### Durable-store and checkpoint behavior

- Treat total transaction-store loss as fail-closed suspension. Start no external dispatch and fabricate no terminal outcome while a stop decision cannot commit; expose no newer state than the last safely readable or cached committed snapshot.
- If the same fenced worker observes store recovery, reconcile every may-have-dispatched call and effect before committing `run_store_unavailable`, unless an earlier stop decision won. If that process died before recording the outage, a fresh worker trusts only durable markers and neither infers nor fabricates the process-local failure.
- If transaction authority never recovers, leave the Resume Run durably nonterminal with its active claim rather than pretending it finished.
- Retire a Draft Basis Checkpoint only after a definitive pre-artifact terminal decision. Retire a Resume Artifact Checkpoint only after the Resume Completion seal, fully verified compensation, or proved zero-effect compensation.
- Treat post-seal checkpoint deletion as idempotent cleanup. Failure never reopens or recounts a Resume Completion. A systemic checkpoint-store failure blocks dependent work, while isolated cleanup failure may retry without blocking unrelated work when safe checkpoint capability remains provable.
- Retain every checkpoint and key needed by Same-Run Artifact Recovery or Resume Artifact Quarantine without time-based expiry.

| Shared provider failure | `provider_request_rejected`, `provider_protocol_failure`, `provider_rate_limit_exhausted`, `provider_unavailable_exhausted`, `provider_transport_exhausted`, `provider_recovery_exhausted` |
| Shared workspace, rendering, storage, checkpoint, or execution failure | `workspace_observation_unstable`, `workspace_unavailable`, `workspace_access_invalid`, `workspace_contract_mismatch`, `artifact_rendering_unavailable`, `artifact_storage_unavailable`, `checkpoint_key_unavailable`, `checkpoint_store_unavailable`, `master_checkpoint_unavailable`, `run_store_unavailable`, `storage_failure_unclassified`, `run_execution_failure` |
| Standard terminal reason | `target_met`, `spend_limited`, `attempt_budget_exhausted`, `queue_exhausted`, `operator_cancelled` |

- Give `pending`, `evaluating`, ordinary forward `recovering`, and `completed` candidates no candidate reason. A `recovering` candidate's quarantine cause belongs to its Resume Artifact Set rather than the candidate.
- Require exactly one semantic candidate reason for `skipped`, `failed`, `cancelled`, and `compensating`. Use `operator_cancelled` for cancellation, retain the definitive cause during compensation and terminal failure, and copy the run reason to an admitted pre-Artifact candidate stopped by the run.
- Clear a candidate reason only when the candidate becomes `completed`. Give every terminal Resume Run exactly one reason consistent with its Outcome, and never change that reason during safe drain or audited late recovery.

### Deterministic reason selection

- Evaluate gates in workflow order and retain the first recorded failing gate. Do not recompute its reason from later evidence.
- Within pre-admission and Admission, evaluate quarantine lock, Application availability, To Apply status, Analyzed status, Match Score presence, Match Score threshold, analysis-score agreement, source completeness, then independent Resume.
- Within continuation, evaluate source availability, eligibility, source equality, then independent Resume. Route ambiguity through bounded workspace recovery rather than a definitive continuation reason.
- Within durable and provider authority, evaluate total run-store availability, checkpoint key, checkpoint store, scoped checkpoint proof, spend authority, generation envelope, rate card, pricing approval, model approval, tokenizer, protocol overhead, provider authentication, then provider balance. A narrower reason requires every earlier capability to remain provably available.
- Within provider dispatch and response, preserve explicit authentication or balance rejection; then locally valid request rejection, required response structure/protocol, returned model, usage/pricing contradiction, finish reason, JSON, and semantic validity. Missing matching billing evidence alone creates an Indeterminate Resume Call.
- Within workspace observation, classify explicit access failure, schema or malformed-success contract failure, bounded incomplete reads, then complete-but-moving observations.
- Within Artifact Set reconciliation, inspect the canonical effect order and, within one effect, checkpoint availability, ownership/cardinality, content/digest, relation proof, then result reconstruction. During compensation, failure to verify the current reverse barrier uses `artifact_compensation_unproven`.
- Use `storage_failure_unclassified` only for an unclassified storage-path defect. Use `run_execution_failure` as the safe Run-Scoped fallback for other caught invariant or worker defects; raw exception details never become the reason.

## Testing Decisions

### Primary acceptance seam

- Exercise the eventual public Resume Run workflow through normal application composition with the real Resume worker, Resumes-owned transaction/checkpoint store, spend policy, and filesystem artifact implementation. Substitute only deterministic provider and workspace adapters, a controlled clock, and explicit fault barriers.
- Start, observe, and cancel through the public application boundary; observe only privacy-safe run snapshots; inspect the deterministic provider ledger, fake workspace, and temporary PDF effects as external collaborators; and recover by constructing a fresh application over the same durable state.
- Make this composed workflow the owner of all operator-visible semantics: start readiness, fixed Resume Candidate Set and backfill, state/outcome/reason mapping, provider and spend stops, source failures, artifact recovery and compensation, quarantine and late Completion, cancellation races, restart and fencing, safe drain, exact counters, behavioral consequences of protected-checkpoint lifecycle, privacy, and immutable stopping decisions.
- Use a table-driven taxonomy fixture so every approved reason has at least one composed end-to-end witness. Assert start acceptance or rejection, failure scope, the candidate reason-presence rules for every Resume Candidate State, the Outcome-consistent and immutable Resume Run reason, backfill eligibility, spend disposition, restart and recovery behavior, Resume Artifact Set/quarantine cause and disposition, and privacy-safe serialization. Keep exact checkpoint-presence and retirement assertions in the transaction/checkpoint-store contract because checkpoints are intentionally absent from public run metadata.
- Prefer external behavior over implementation details. Do not assert private helper calls, physical table layout, worker polling cadence, or checkpoint ciphertext representation from the composed suite.

### Focused contract seams

- Add a Resume transaction and checkpoint-store contract for atomic boundaries that cannot be isolated reliably through the public workflow alone: admission, reservation and dispatch marker, Requirements checkpoint, Draft-to-Artifact transition, effect intent/evidence, stopping decision, Completion seal, concurrent admission, single-active-run enforcement, lease fencing, rollback, restart, key failure, checkpoint retirement, safe-column allowlists, and both run-store outage branches.
- Add a prepared-provider and spend contract for render-once/send-exactly-once behavior, exact stage envelopes, the two-attempt ceiling and consumption semantics per stage, no fallback or nested retry, deadlines, response classification, authorization, and settlement. Exercise every reachable attempt sequence drawn from usable output, unusable output, rate limit, server/resource failure, proven `not_transmitted`, and may-have-transmitted transport/Indeterminate result, including every two-attempt sequence that continues past a non-usable first result. Add scripted usable-first cases that prove the queued second result is never consumed, plus every immediate authentication, balance, request, protocol, returned-model, usage, and pricing defect. Explicitly prove that proven non-transmission releases the reservation but not the consumed stage attempt, and that usable output may advance with an Indeterminate reservation.
- Add one workspace conformance contract and run it against both the deterministic workspace and the recorded Notion adapter. Cover complete source properties/body/relations, pagination and recursion, `AA`/`ABB`/`ABA`, incomplete reads, cursor cycles, ever-growing pagination, whole-pass deadline, constituent retry bounds, cancellation barriers, exact Artifact Set lookup including archived cardinality, enhanced-Markdown semantic round-trip, status normalization, lost-response reconciliation, relation-last readback, and compensation barriers. Assert that each Resume and Note creation is exactly one enhanced-Markdown `POST /v1/pages` carrying the complete content and properties, with one write transmission per durable attempt and zero `/blocks/.../children` append requests or asynchronous content tasks.
- Add a PDF artifact/evidence contract for full Resume Artifact Set ID addressing, write-ahead staging, atomic exposure, non-overwrite behavior, deterministic checkpoint rerender, document and PDF-byte digests, index reconstruction, filename collisions, missing/corrupt/mismatched state, and exact-owned removal. Keep digest serialization golden vectors within this contract rather than creating another orchestration seam.
- Do not add parallel controller-, service-, worker-, and repository-level suites that repeat the same workflow matrix. Use focused contracts only where exhaustive fault combinations or atomicity cannot be observed cleanly from the primary seam.

### Required behavior matrices

- Test multi-defect reason precedence at every gate, including all Admission fields failing together, source change plus independent Resume, wrong provider model plus malformed output and contradictory usage, multiple artifact invariant failures, and overlapping run-store, checkpoint, and spend failures.
- Cover stable-observation sequences `AA`, `ABB`, and `ABA`; incomplete constituent reads at every pagination, body, and relation boundary; cursor cycles and growing pagination; timeout, rate-limit, server, access, contract, and malformed-success responses; and outer-deadline exhaustion. During pre-Artifact admission and provider-continuation observation, cancel before and between every constituent request, including between transport attempts, and prove no later attempt, request, pagination step, or observation begins. For an existing Resume Artifact Set, prove cancellation still permits bounded, fenced source checks, reconciliation and readback, Resume Completion Gates, and compensation verification, while none can authorize a new candidate or provider call. Assert the logical-observation, whole-pass, and constituent-request bounds.

Cover explicit rejection, affirmative non-dispatch, lost response, zero/one/multiple/mismatched readback, unavailable reconciliation, both permitted attempts, and the page-create no-resend rule.

- Place cancellation barriers before and after Resume Candidate Admission, reservation, may-have-dispatched marker, every Requirements and Draft result class, Draft-to-Artifact transition, PDF staging, every artifact intent/mutation/observation, pre- and post-attachment gates, Resume Completion seal, quarantine, compensation, and worker claim.

- Remove provider or spend authority after a Resume Artifact Set exists and prove deterministic recovery and sealing continue without an `authorization_blocked` decision unless another provider call is actually required.
- Test quarantine backfill, safe active-claim release, audited late seal, Completion count equal to and above target, immutable earlier outcome, compensation-only quarantine, and the fixed Resume Candidate Set bound on overshoot.
- Simulate total run-store outage and prove zero new external dispatch and no fabricated terminal write. - Test Master Source Checkpoint retirement at queued cancellation. Test Draft Basis Checkpoint retirement after pre-Artifact cancellation or definitive failure. Test Resume Artifact Checkpoint retirement after zero-effect compensation, Resume Completion seal, or full verified compensation; retention under Resume Artifact Quarantine; and post-terminal deletion failure without reopening or recounting work.

### Test quality and prior art

- Use deterministic provider and workspace fakes, a controlled clock, and explicit lease, PDF, and store fault barriers around the real filesystem artifact and transaction/checkpoint implementations where the seam requires them. Use monotonic fake time for deadline cases, fresh application composition for restart, and no timing sleeps, paid provider calls, or live Notion mutations.

- Use existing Notion fake/recorded conformance tests as prior art for pagination, recursive content, normalized errors, retry-safe reads, relation-last behavior, ambiguous creation, and cleanup verification.
- Use existing Resume execution-recovery tests as prior art for lost create responses, restart reconciliation, mutation exclusion, and unverified-artifact blocking; migrate the durability prototype's crash, checkpoint, quarantine, source-proof, fencing, and lost-effect scenarios into production acceptance cases rather than keeping the prototype as a production seam.

## Out of Scope

- Public route names, operation IDs, request and response field names, polling behavior, presentation retention, retry-eligibility presentation, cancellation HTTP semantics, public audit representation, download/result-link transport, and operator quarantine inspection or recovery commands; the operator-visible contract owns those decisions.
- Dashboard interaction, wording, and visual state presentation; the dashboard prototype owns those decisions after the public contract is settled.
- Exact retry backoff durations, worker polling cadence, physical table layout, private helper names, migration mechanics, and scheduling details, provided they preserve attempt ceilings, transaction order, fencing, safe drain, and privacy.
- Production checkpoint-key provider selection, secret delivery, backup-retention periods, and execution of live-store migrations. Operational choices may not weaken authenticated checkpoint protection, fail-closed readiness, quarantine retention, or logical retirement.
- Changing the accepted Resume Generation Envelope, model choices, reasoning mode, output ceilings, provider deadlines, two-attempt stage limit, or no-fallback policy.
- Changing the fixed $1.00 Resume Run Spend Ceiling, exact reservation arithmetic, conservative settlement, or Indeterminate Resume Call treatment.
- Reopening the Resume Candidate Set, Resume Attempt Budget, source-version, revalidation, Resume Completion Gate, or immutable Resume Completion contracts.
- Reopening Resume Artifact Set ID ownership, canonical effect order, forward recovery, compensation barriers, quarantine mutation lock, or the atomic Resume Completion seal.
- Replacing the Resumes-owned transactional SQLite boundary, checkpoint kinds, authenticated-encryption requirement, or the prior decision not to reuse the Analysis schema or begin with a generic durable-run kernel.
- Changing Application Analysis behavior, public contracts, ledger, failure taxonomy, or permitted concurrency with Resume Runs.
- Historical artifact repair, replacement, retirement, background monitoring, or automatic response to Historical Artifact Drift.
- Adopting, modifying, archiving, detaching, or counting independently existing Resumes as this run's work.
- Parallel Resume candidates, parallel Resume provider calls, multiple active Resume Runs, or queuing a second Resume Run.
- Rolling back earlier Resume Completions after any later failure, spend limit, cancellation, or recovery result.
- Implementing the durable Resume Run product within this decision and specification ticket.

## Further Notes

- Current Notion transport behavior retries `PATCH /pages/...` beneath one logical call. Durable Resume artifact work must opt out of that behavior so one durable effect attempt can never hide multiple mutation transmissions.
- The exceptional late-Completion rule is documented in ADR 0002 because it deliberately trades a strict target ceiling for truthful recovery of already-owned work without letting quarantine hold the whole run open.
- Cancellation-driven forward recovery is a consequence of the existing Resume Artifact Set ID and forward-recovery decision, not a separate artifact-ownership architecture.
- “Cancellation stops work” is unsafe shorthand: cancellation stops later Resume Candidate Admission and provider calls, while billing settlement, established Resume Artifact Set recovery, required compensation, and reconciliation continue to a safe boundary.
- “Retry” is intentionally split into logical source-observation attempts, constituent read transport attempts, provider-stage durable dispatch attempts, durable artifact-effect attempts, reconciliation, and candidate backfill. They have different bounds and must not share an implicit counter.
- “Finished snapshot is immutable” is too broad: the winning Resume Run Outcome and reason are immutable, while a `recovering` candidate and truthful Resume Completion count may change through audited late proof.
- “Resume Batch Target is a hard maximum” is false for already-owned potentially sealable work. Normal scheduling stops at the target; ADR 0002 permits bounded late overshoot without outcome rewriting.
- “Indeterminate output” is not canonical. Indeterminate Resume Call describes billing/accounting evidence and may coexist with usable provider output.
- Resume Committed Spend is not actual spend: it includes verified cost, active reservations, and complete reservations retained for Indeterminate Resume Calls.
