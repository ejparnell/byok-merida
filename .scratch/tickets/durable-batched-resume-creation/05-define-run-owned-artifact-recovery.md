# Define run-owned artifact identity and same-run recovery

Parent: [Wayfinder: Durable Batched Resume Creation](map.md)

Type: grilling

Status: ready-for-agent

State: closed

Assignee: codex

Blocked by: none

## Question

What evidence proves that a Job-Specific Resume, Resume Fit Analysis Note, PDF, and final Resume-to-Application relation belong to one Resume Run candidate across every crash or ambiguous Notion/PDF effect, and which same-run partial states may resume, complete, compensate, quarantine, or require operator recovery without adopting independently existing artifacts?

The decision should cover ambiguous Notion creation, relation-last completion, effect and cleanup ordering, per-candidate journal identity, staged-file ownership, safe result-link reconstruction, multiple roles at one company without PDF filename collision, and the current documentation/code disagreement about PDF-versus-Note commit order while leaving historical missing-artifact repair out of scope.

## Decisions

- Before its first artifact effect, each Resume Run candidate receives one opaque, immutable Resume Artifact Set ID that the durable run store maps to that exact run, candidate, and Application.
- `Merida Artifact ID` is a required rich-text property in both the Notion Resumes and Notes databases. Each page receives the Resume Artifact Set ID in its initial create request, and staged and published PDF metadata carries the same identity.
- Recovery may claim a remote artifact only when the correct database contains exactly one page in total with the Resume Artifact Set ID and that page is active and has the expected relations and content. Archived pages participate in this cardinality check: an active page plus an archived duplicate is multiple matches, not a unique owned artifact. Titles, company, role, timestamps, content, filenames, and independently existing relations are not ownership evidence. Zero or multiple matches require quarantine and evidence-backed recovery.
- The final Resume-to-Application relation remains the Resume Completion commit marker and is attached only after the run verifies its keyed Job-Specific Resume, keyed Resume Fit Analysis Note, and keyed PDF. A durable run-store state alone cannot manufacture a completion.
- After an ambiguous final attach, recovery rereads Notion. The exact expected relation plus a valid complete Resume Artifact Set records a Resume Completion and safely reconstructs result links; an absent relation may be set again idempotently only after the other artifacts revalidate. A wrong or additional relation, a missing or mismatched artifact, or an independently existing relation never counts as this run's completion.
- Same-Run Artifact Recovery is forward-only for a uniquely owned, structurally valid partial set: recovery observes the keyed artifacts rather than trusting a possibly stale journal phase, preserves each verified effect, and performs only missing effects with the same Resume Artifact Set ID and exact accepted artifact content.
- A restart never reruns provider generation, creates a replacement keyed Resume or Note, assigns a new Resume Artifact Set ID, or compensates valid effects merely because execution was interrupted. Compensation begins only when later policy has definitively stopped that candidate and every owned effect is safely identifiable; ambiguous ownership, effect outcome, or cleanup requires quarantine instead of guessing.
- The canonical effect order is: durably record the Resume Artifact Set intent; stage its PDF; create or reconcile the unlinked Job-Specific Resume; publish or reconcile the PDF; create or reconcile the Resume Fit Analysis Note; validate the complete set; then attach and reread the final Resume-to-Application relation. Recovery never skips an earlier invariant merely because a later effect is visible.
- Artifact recovery has one logical durable record keyed by Resume Artifact Set ID, with its parent Resume Run, candidate identity and ordinal, and Application recorded separately. A Resume Run ID is not an artifact-journal key because one run owns multiple candidate artifact sets.
- Before every artifact mutation, the owning record durably captures effect intent; afterward it records observed safe evidence. These are reconciliation facts rather than an authoritative current phase: restart recovery compares them with observed Notion and PDF state. One candidate's evidence is never overwritten when the run advances, every Artifact Set ID is never reused and retains at least the tombstone needed to prove non-reuse, completed and compensated records are terminal, and quarantine may transition only through verified resolution. The record belongs to Resumes-owned durable run state; the durability prototype owns its physical schema, retention representation, and transaction boundaries.
- Staged and published PDFs use deterministic, non-overwriting storage paths addressed by the full Resume Artifact Set ID. Before the staged file becomes visible, the recovery record captures the exact PDF SHA-256; a file is owned and reusable only when its Artifact Set ID, expected path, and digest all agree.
- PDF staging uses a write-ahead ownership boundary. Merida renders to an unowned private temporary file, computes the Resume Artifact Document Digest and exact PDF-byte SHA-256, and durably records those values with the Artifact Set ID, expected final staging path, and staging intent before atomically exposing the staged file at that path. A crash with durable evidence but no staged file may rerender from the same checkpoint; unowned temporary residue is ignored and may be garbage-collected; a final staged file without matching prior evidence requires quarantine. The durability prototype owns the physical atomic-write mechanics.
- The PDF index is keyed primarily by Resume Artifact Set ID and may additionally map the observed Resume ID for lookup. Result links are reconstructed from that verified index. Human-facing downloads use the fixed candidate source to present `{Company}-{Role}-{User}.pdf`, while the distinct ID-addressed storage path prevents collisions between multiple roles, repeated pursuits, or similarly named Applications at one company. Legacy or merely human-named files are never adopted into a run.
- Each Job-Specific Resume and Resume Fit Analysis Note is created synchronously in one Notion `POST /v1/pages` containing its initial properties, Resume Artifact Set ID, required initial relations, and complete canonical enhanced-Markdown body. Before dispatch, the recovery record captures an Artifact Request Digest over the exact enhanced-Markdown request bytes. Resume artifact creation does not use post-create block appends or asynchronous Notion tasks.
- After an ambiguous page create, recovery queries the correct database by exact Resume Artifact Set ID and retrieves the complete Markdown. Exactly one total keyed page, which must be active and have the expected properties, relations, non-truncated content, no unknown blocks, and matching canonical digest, is the same-run artifact. No match remains quarantined for recheck and is never recreated without affirmative non-dispatch evidence; multiple total matches—including archived duplicates—or any structural/content mismatch require evidence-backed recovery.
- Resume artifact readiness requires the Notion `2026-03-11` enhanced-Markdown create/read behavior, required connection capabilities, and a proved semantic round trip for every block type Merida may generate. The legacy multi-request block-append path is not an accepted durable commit seam.
- Unprovable artifact ownership, content, relation state, or cleanup creates a durable Resume Artifact Quarantine for the exact Resume Artifact Set and Application. Quarantine is an Application-scoped mutation lock rather than a terminal artifact disposition: while it exists, automatic creation, attachment, compensation, and later Resume Run evaluation for that Application are prohibited; read-only inspection and safe reconciliation remain allowed.
- Quarantine never expires because of time, lease loss, restart, cancellation, or the owning run finishing. It may exit only through an audited reconciliation that proves one of three states: affirmative non-dispatch plus otherwise valid observed state returns the original Artifact Set to Same-Run Artifact Recovery; a valid committed set proceeds to sealing; or unambiguous ownership plus controlled recovery authorization enters strict compensation. The compensation path must finish and verify every owned effect before the Application is unblocked. A generic acknowledgement cannot authorize a mutation or unblock the Application. After proven compensation, a future run may evaluate the Application with a new Resume Artifact Set ID, but the original run never reevaluates that candidate. The durability and public-contract tickets own the evidence representation and operator transport; the failure-policy ticket owns whether quarantine stops the current run or permits backfill.
- Compensation is a strict verified reversal: clear and verify the owned Resume's Application relation; archive and verify the owned Note; remove and verify the owned published PDF; archive and verify the owned Resume; then remove any remaining staged PDF and active lookup entry. Only afterward does the recovery record become terminally compensated while retaining its identity, effect, and cleanup evidence.
- Every compensation step is a barrier. If its intended state cannot be verified, cleanup stops and the Artifact Set enters quarantine without dismantling lower effects. Cleanup is addressed only through exact Artifact Set ownership and is safely repeatable; an already verified Resume Completion is never compensated, and a missing artifact counts as cleaned only when its expected identity and location are unambiguous.
- Recovery reconstructs result summaries only after fresh readback validates the complete Artifact Set and final relation. It uses the current exact keyed Resume and Note identities and Notion URLs, the digest-verified Artifact Set PDF index and backend download route, and the Artifact Set's finalized normalized download basename; it never depends on cached response objects, transient URLs, raw source fields, or filesystem paths.
- Durable recovery state retains stable artifact identities and verification evidence rather than presentation links. Before a completion is sealed, any result link that cannot be reconstructed prevents that candidate from reporting a Resume Completion and instead causes reconciliation or quarantine. The public-contract ticket owns the eventual route and response field names.
- Before the first artifact effect, Merida atomically persists a recovery-scoped private Resume Artifact Checkpoint containing the exact validated canonical Resume and Note documents, bound to the Resume Artifact Set ID with both document digests. This checkpoint is required because content-free metadata, the Resume page, and the staged PDF cannot reconstruct every missing artifact without rerunning provider work.
- The checkpoint is isolated from public run metadata and the content-free spend ledger and contains no prompts, reasoning, raw provider responses, Job Content, or Master Resume source. It exists only for same-run rendering, verification, and forward recovery and is removed after the Artifact Set is terminally completed or compensated. Because quarantine does not expire, a required checkpoint may outlive its owning run while the Application remains locked. Missing or corrupt required checkpoint content causes quarantine, never provider regeneration. The durability prototype owns its smallest protected physical representation, at-rest protection, atomic write boundary, and any future evidence-preserving retirement semantics.
- A Resume Completion seals its Artifact Set only through one logical atomic commit that records the candidate's single completion and run progress, the Artifact Set's terminal sealed state, its compact permanent ownership record, and its stable result identities together. A crash before that commit leaves an unsealed set that recovery rereads and may seal; a crash after it can neither count the candidate again nor reopen or compensate the set. The durability prototype owns the physical transaction.
- After the seal commit, Merida deletes the private checkpoint as retryable cleanup. A sealed set with leftover checkpoint data remains terminal and restart cleanup deletes only that residue. The compact record maps the Application and Resume Artifact Set ID to the committed artifact identities and digests and retains the already-finalized normalized download basename as immutable safe presentation metadata. It does not retain the raw Company, Role, or user source fields solely for naming, and the basename is never ownership evidence. This record outlives any presentation-oriented run-history retention; the public-contract ticket owns filename normalization and the download route.
- Later removal or mutation of a sealed Resume, Note, PDF, or relation is Historical Artifact Drift. This initiative adds no background monitor or new artifact lifecycle state for it. A normal supported read or operator inspection that happens to discover drift may report a read-only diagnostic, but the observation never changes the original run's completion count, reopens or compensates the sealed set, invokes Same-Run Artifact Recovery, or makes the Application eligible for a new Resume Run. The public-contract ticket may expose that diagnostic; a future dedicated historical repair or explicit retirement workflow must own any action.
- If a Stable Resume Source Observation proves that a different active Job-Specific Resume appeared before this run sealed its Resume Completion, the run never adopts, modifies, archives, or counts that independent artifact. When every run-owned effect and the relation state are unambiguous, Merida clears its own relation if necessary and strictly compensates only its own Artifact Set; the candidate earns no Resume Completion. Ambiguous relation or ownership state enters quarantine. The failure-policy ticket owns classification and backfill.
- Resume and Note semantic identity use separate versioned Artifact Document Digests calculated from every ordered document block's exact kind, nonnegative depth, and text. Digest v1 accepts the current domain block vocabulary—`heading_1`, `heading_2`, `heading_3`, `paragraph`, `quote`, `callout`, `bulleted_list_item`, `numbered_list_item`, and `toggle`—normalizes text only to Unicode NFC and LF line endings, and otherwise preserves whitespace, punctuation, and case. It hashes a version-tagged, unambiguous UTF-8 encoding. The durability prototype selects the precise canonical serialization and publishes golden digest vectors without changing these semantics.
- Recovery parses complete retrieved enhanced Markdown back into that canonical representation and compares its digest; raw returned Markdown bytes are not semantic identity because Notion may normalize equivalent formatting. Unknown block kinds, negative or invalid depths, truncation, parse loss, or unsupported normalization fail closed. Resume artifact readiness proves a semantic enhanced-Markdown round trip for every accepted block kind.
- Effect evidence additionally retains the Artifact Request Digest of each exact enhanced-Markdown request. The recovery record and PDF index bind the PDF to the same canonical Resume Artifact Document Digest as the Resume page and retain a separate PDF Byte Digest over the exact PDF bytes. Truncated or unknown Notion content, parse failure, any semantic mismatch, or any PDF byte mismatch requires quarantine; visual or textual similarity is not evidence.

## Recovery Classification

| Observed state | Automatic disposition |
| --- | --- |
| Effect not attempted, or affirmative non-dispatch evidence exists | Resume at that missing effect with the same Resume Artifact Set ID. |
| Valid checkpoint and staged PDF with matching write-ahead path and digest evidence | Continue with Job-Specific Resume creation. |
| Staging intent and digest evidence exist but the final staged file does not | Rerender from the same checkpoint and expose only the exact expected bytes; never call the provider. |
| Unowned private staging temporary residue | Ignore or garbage-collect it; never adopt it as an Artifact Set effect. |
| Final staged path exists without matching prior ownership and digest evidence | Quarantine; never infer ownership from the path or bytes alone. |
| Exactly one keyed Resume with matching properties and Artifact Document Digest | Preserve it and continue with PDF publication. |
| Valid ID-addressed PDF with matching document and byte digests | Preserve it and continue with Note creation. |
| Exactly one keyed Note with matching relations and Artifact Document Digest | Preserve it and continue toward the Resume Completion Gate. |
| Ambiguous Notion create with exactly one subsequently verified match | Record its observed page identity and continue. |
| Ambiguous Notion create with zero or multiple total keyed pages, including archived pages | Quarantine; never resend automatically. Affirmative non-dispatch evidence may return the original Artifact Set to recovery. |
| Previously observed Resume or Note is missing, archived, altered, or structurally wrong | Quarantine; never create a replacement page. |
| Missing or corrupt pre-completion PDF | Re-render only from the same checkpoint and accept only the expected digests; otherwise quarantine. |
| Complete verified set with final relation absent | Attach or safely repeat the idempotent final relation. |
| Complete verified set with the exact relation and successful Stable Resume Source Observation | Atomically record one Resume Completion, run progress, terminal seal, compact ownership evidence, and stable result identities; then delete the private checkpoint as retryable cleanup. |
| Crash before the logical seal commit | Treat the set as unsealed, freshly revalidate it, and perform the single seal commit when valid. |
| Crash after the logical seal commit but before checkpoint deletion | Preserve the one completion and sealed state and delete only the leftover checkpoint; never recount, reopen, or compensate. |
| Independent Resume or definite source invalidation before completion | Compensate only the run-owned Artifact Set when every state is unambiguous; otherwise quarantine. |
| Compensation partially complete | Continue strict reverse compensation from the first unverified barrier. |
| Required checkpoint missing or corrupt while effects remain | Quarantine; never regenerate through the provider. |
| Quarantined Artifact Set | Permit read-only reconciliation only until an audited decision proves same-set recovery, complete commitment, or controlled strict compensation; generic acknowledgement has no effect. |
| A normal supported read or operator inspection observes that a sealed Artifact Set later lost or changed an artifact | Report Historical Artifact Drift as a read-only diagnostic when supported; do not reopen, repair, replace, or add a monitor or lifecycle transition through this initiative. |

Titles, filenames, timestamps, content similarity, and independently existing relations never change a partial state into a same-run artifact.

## Answer

Each Resume Run candidate owns one Resume Artifact Set identified before its first artifact effect by an opaque, immutable Resume Artifact Set ID. The same exact ID is written to the generated Resume, Resume Fit Analysis Note, staged and published PDF metadata, and the Resumes-owned recovery record. Merida claims an artifact only from a unique exact keyed match with valid content and relations; names, timestamps, filenames, similarity, and independently existing artifacts never prove ownership.

Before effects begin, Merida persists the exact validated Resume and Note documents in a recovery-scoped private Resume Artifact Checkpoint and records separate semantic, request-byte, and PDF-byte digests. Recovery then observes actual Notion and PDF state, preserves every uniquely owned valid effect, and advances only through missing effects in the canonical order. Ambiguity creates a durable Application-scoped quarantine. A later policy decision may trigger strict verified compensation, but interruption alone never destroys valid work or reruns provider generation.

The Resume-to-Application relation remains the final commit marker. A Resume Completion counts only after fresh validation of the complete Artifact Set and source, successful relation readback, and one logical atomic commit of completion progress, terminal seal, stable result identities, and compact permanent ownership evidence. Checkpoint deletion is retryable cleanup. Later mutation of a sealed artifact is read-only Historical Artifact Drift, not same-run recovery or permission to create a replacement.

## Problem Statement

An operator can start a Resume Run whose artifact work crosses a private local checkpoint, local PDF storage, two Notion databases, and the final Application relation. The backend may restart or lose a response before or after any one of those mutations. Today, a run-level effect journal cannot distinguish multiple candidates, a Notion page has no run-owned marker, PDF names can collide, and cleanup-oriented retry can destroy valid work or create replacements after an ambiguous result. A title, relation, filename, or similar body can also resemble run-owned work without proving that the run created it.

The operator needs every Resume Completion to mean that one exact run candidate produced one complete and verifiable Job-Specific Resume, Resume Fit Analysis Note, PDF, and final relation. Restart must continue accepted work without another provider call, duplicate page, overwritten PDF, adopted independent artifact, or false completion. When safety cannot be proven, uncertainty must remain durable and block conflicting mutations rather than disappear with time, acknowledgement, cancellation, or run completion.

## Solution

Merida assigns one Resume Artifact Set ID to each candidate before its first artifact effect and binds it to the Resume Run, candidate identity and ordinal, and Application. Generated Resume and Note pages carry that ID in a required `Merida Artifact ID` property, while PDF storage and recovery evidence use the same identity. Exact keyed cardinality, complete content, expected relations, paths, and digests establish ownership.

Before staging begins, Merida atomically stores the exact validated Resume and Note documents in a recovery-scoped private checkpoint. Versioned Artifact Document Digests prove their canonical block semantics; Artifact Request Digests prove the exact enhanced-Markdown request bytes; and a PDF Byte Digest proves the rendered file bytes. The checkpoint contains no prompts, reasoning, raw provider response, Job Content, or Master Resume source and is isolated from public run and spend metadata.

Effects advance in one order: durable Artifact Set intent, write-ahead PDF staging, unlinked Resume creation, PDF publication, related Note creation, complete-set validation, and relation-last commit. Resume and Note creation each use one synchronous Notion enhanced-Markdown page request. Restart observes the real workspace and filesystem, preserves every valid owned effect, and performs only the earliest missing effect with the original ID and checkpoint content.

Unprovable ownership, content, relation, result-link, or cleanup state creates Resume Artifact Quarantine for the Artifact Set and Application. Quarantine locks automatic mutation and later Resume Run evaluation while allowing read-only reconciliation. Only audited evidence may return the same set to recovery after proven non-dispatch, prove it complete and seal it, or authorize strict compensation of uniquely owned effects. A generic acknowledgement has no effect.

Completion is relation-last and exactly once. Fresh readback validates the keyed Resume, Note, PDF, stable source, result identities, and exact final relation before one logical atomic seal records the Resume Completion, run progress, permanent ownership evidence, and stable result identities. A compact record retains safe IDs, digests, a non-reuse tombstone, and the finalized normalized download basename after private checkpoint and presentation history cleanup. Later discovered artifact changes are Historical Artifact Drift and cannot reopen, repair, compensate, or replace the sealed result through a Resume Run.

75. As an operator, I want result summaries reconstructed only after fresh validation of the complete Resume Artifact Set and final relation, so that stale response objects cannot expose false success.
76. As an operator, I want reconstructed results to use current keyed Resume and Note identities and Notion URLs plus the digest-verified PDF index and backend route, so that links survive restart.
77. As an operator, I want any unreconstructable required result link to prevent sealing and trigger reconciliation or quarantine, so that every reported Resume Completion has usable outputs.
78. As a maintainer, I want durable recovery state to retain stable identities, digests, and verification evidence rather than transient URLs or filesystem paths, so that persistence remains safe and portable.
79. As an operator, I want one logical atomic seal to record the candidate's single Resume Completion, Resume Run progress, terminal Artifact Set state, compact ownership record, and stable result identities together, so that progress cannot diverge from artifact commitment.
80. As an operator, I want a crash before the seal treated as an unsealed set requiring fresh validation, so that recovery can seal it exactly once.
81. As an operator, I want a crash after the seal unable to recount, reopen, or compensate the Artifact Set, so that Resume Completion is idempotent.
82. As a maintainer, I want checkpoint deletion after sealing to be retryable cleanup, so that leftover private content does not change terminal state.
83. As a maintainer, I want completed and compensated checkpoints removed while compact safe ownership evidence remains, so that private recovery content has bounded terminal retention.
84. As an operator, I want the compact ownership record and finalized normalized download basename to outlive presentation-oriented Resume Run retention, so that committed identity and naming remain reconstructable.
85. As an operator, I want the normalized basename immutable after sealing and excluded from ownership evidence, so that later source edits cannot rename or claim artifacts.
86. As an operator, I want later loss or mutation of a sealed Resume, Note, PDF, or relation classified as Historical Artifact Drift, so that it is not confused with unfinished same-run work.
87. As an operator, I want Historical Artifact Drift reported only as a read-only diagnostic when a supported read happens to discover it, so that this initiative does not silently introduce monitoring.
88. As an operator, I want Historical Artifact Drift never to change the original Resume Completion count, reopen or compensate the Artifact Set, invoke Same-Run Artifact Recovery, or make the Application eligible again, so that sealed history remains stable.

## Implementation Decisions

- Resume artifact recovery belongs to the Resumes context. Notion remains authoritative for completed Resume and Note pages, while the backend owns durable coordination, private recovery content, PDF identity, and completion evidence.
- Before its first artifact effect, each candidate receives one opaque, immutable Resume Artifact Set ID. The recovery record maps it to the exact Resume Run, candidate identity and ordinal, and Application.
- Artifact Set IDs are never reused. Terminal retention must preserve at least the minimum tombstone needed to prove non-reuse; the durability prototype chooses its physical representation and retention mechanics.
- Generated Resumes and Notes require a rich-text `Merida Artifact ID` property containing the Artifact Set ID. The Master Resume leaves this property empty. Staged and published PDF evidence carries the same ID.
- Recovery queries the correct Notion database by exact Artifact Set ID and counts every keyed page, including archived pages. Ownership requires exactly one total keyed page that is active and has the expected properties, relations, complete content, and semantic digest.
- Titles, company, role, timestamps, filenames, content similarity, and independently existing relations are never ownership evidence. Zero, multiple, archived-only, malformed, or mismatched results cannot be adopted.
- One logical per-candidate recovery record is keyed by Artifact Set ID. It records write intent before every mutation and safe observed evidence afterward, but observed Notion and PDF state outrank a stale recorded phase.
- Before the first effect, Merida atomically persists a recovery-scoped private Resume Artifact Checkpoint containing only the exact validated canonical Resume and Note documents plus minimal identity and digest bindings.
- The checkpoint is isolated from public run metadata and the content-free spend ledger. It excludes prompts, reasoning, raw provider responses, Job Content, Master Resume source, and other input evidence.
- A checkpoint may outlive its owning Resume Run while quarantine remains unresolved. It is deleted only after verified completion or compensation under this policy; ticket 06 must choose at-rest protection, atomic storage, and any future evidence-preserving retirement semantics.
- Resume and Note each have a separate versioned Artifact Document Digest over ordered `(kind, depth, text)` blocks. Digest v1 accepts headings 1–3, paragraph, quote, callout, bulleted item, numbered item, and toggle; it normalizes text only to Unicode NFC and LF line endings and otherwise preserves bytes semantically.
- Ticket 06 chooses the unambiguous version-tagged UTF-8 serialization and publishes golden digest vectors. Unknown kinds, invalid depth, truncation, parse loss, and unsupported normalization fail closed.
- Each Notion page effect records an Artifact Request Digest over the exact enhanced-Markdown request bytes before dispatch. Raw returned Markdown bytes are not semantic identity because equivalent formatting may be normalized.
- The PDF recovery record and index bind the Artifact Set ID and Resume Artifact Document Digest to a separate PDF Byte Digest over the exact rendered bytes. A PDF filename or byte digest alone does not establish document ownership.
- Durable Resume Run readiness requires the Notion `2026-03-11` enhanced-Markdown create/read behavior, required insert/read capabilities, complete keyed lookup, and semantic round-trip proof for every accepted block kind before provider or artifact work may begin.
- Each Resume and Note is created synchronously through one `POST /v1/pages` request containing the complete enhanced-Markdown body, Artifact Set ID, initial properties, and required initial relations. Post-create child-block appends and asynchronous page tasks are not part of the durable seam.
- The Resume is initially unlinked from its Application. The Note is created with the exact Application and run-owned Resume relations. The final Resume-to-Application relation remains the commit marker.
- The canonical effect order is: persist Artifact Set intent and checkpoint; stage PDF; create or reconcile the unlinked Resume; publish or reconcile the PDF; create or reconcile the Note; validate the complete set; attach and reread the final relation.
- Same-Run Artifact Recovery is forward-only for a uniquely owned valid partial set. It preserves every verified effect and performs only the earliest missing invariant with the same Artifact Set ID and checkpoint content.
- Restart never reruns provider generation, creates a replacement keyed Resume or Note, assigns a new Artifact Set ID, or compensates valid work merely because execution was interrupted.
- PDF staging renders to an unowned private temporary file. Merida computes the Resume document and PDF byte digests and durably records them with staging intent and expected final path before atomically exposing the staged file.
- Durable evidence without a staged file permits deterministic rerender from the checkpoint. Unowned temporary residue is ignored or garbage-collected. A final staged file without matching prior evidence is quarantined.
- Staged and published storage paths are deterministic, non-overwriting, and addressed by the full Artifact Set ID. The PDF index is keyed primarily by Artifact Set ID and may add a Resume ID lookup after the page identity is observed.
- Human-facing downloads use one finalized normalized `{Company}-{Role}-{User}.pdf` basename derived from the fixed Resume Candidate Source Version. The basename is presentation metadata, not ownership evidence; ticket 08 owns normalization and route details.
- Ambiguous page creation is reconciled through exact keyed lookup and complete enhanced-Markdown readback. One valid total match is preserved. Zero or multiple matches never trigger an automatic resend unless affirmative non-dispatch evidence first returns the original set to recovery.
- A previously observed Resume or Note that becomes missing, archived, changed, or structurally invalid is quarantined and never replaced. A missing pre-completion PDF may be rerendered only from the same checkpoint and must reproduce the expected document and byte digests.
- Resume Artifact Quarantine is a durable Application-scoped mutation lock. While active it prohibits automatic create, attach, compensate, and later-run evaluation while permitting read-only inspection and reconciliation.
- Quarantine has no timeout and survives restart, lease loss, cancellation, and owning-run completion. Generic acknowledgement cannot mutate artifacts or unlock the Application.
- An audited reconciliation may return a quarantined set to recovery after affirmative non-dispatch, proceed to sealing after proving a valid committed set, or enter strict compensation after proving exact ownership and controlled mutation authority. Ticket 08 owns the operator transport and audit presentation.
- Compensation begins only when ticket 07's policy definitively stops the candidate and all run-owned effects are unambiguous. It never applies to a sealed Resume Completion.
- Compensation proceeds through strict verified barriers: clear and verify the owned Resume relation; archive and verify the Note; remove and verify the published PDF; archive and verify the Resume; remove staged residue and the active lookup; then record terminal compensation and retain safe evidence.
- A failed or ambiguous compensation verification stops cleanup before any lower effect is changed and reestablishes quarantine. Restart resumes from the first unverified barrier, and every action is addressed only by exact Artifact Set ownership.
- The Resume Completion Gate performs fresh complete-set and Stable Resume Source Observation checks before attachment and rereads the full state afterward. An absent exact relation may be safely repeated only after all other invariants revalidate.
- Completion requires the exact sole expected relation and a valid keyed Resume, Note, PDF, source observation, and reconstructable result identities. Wrong or additional relations, independent artifacts, mismatches, or run-store flags alone never count.
- One logical atomic seal commits the candidate's single Resume Completion, Resume Run progress, terminal Artifact Set state, compact permanent ownership record, and stable result identities together. Ticket 06 owns the physical transaction.
- A crash before the seal leaves an unsealed set that must be freshly revalidated. A crash after it cannot recount, reopen, or compensate the set; it may only retry deletion of leftover checkpoint data.
- The compact ownership record retains the Application and Artifact Set IDs, stable Resume/Note/PDF identities, semantic/request/file digests needed for evidence, the non-reuse tombstone, and the finalized normalized basename. It contains no private document content, transient URL, or filesystem path and outlives presentation-oriented run history.
- If a different active Job-Specific Resume appears before sealing, Merida never adopts, modifies, archives, or counts it. Unambiguous state may compensate only the run-owned set; ambiguity creates quarantine. Ticket 07 owns the resulting candidate/run classification.
- A sealed set is immutable run history. Later artifact or relation mutation is Historical Artifact Drift, which may be reported as a read-only diagnostic during an ordinary supported read but never reopens, repairs, compensates, replaces, or requeues the result.
- This initiative adds no background Historical Artifact Drift monitor or separate drift lifecycle. A future explicit repair or retirement workflow must own any mutation of sealed history.

## Testing Decisions

- Tests assert observable Resume Run snapshots, provider-call counts, Notion-visible pages and relations, PDF effects, durable completion counts, mutation locks, and restart outcomes. They do not assert private helper names, physical table names, worker cadence, lease timing, or the checkpoint representation selected by ticket 06.
- The primary acceptance seam is the eventual public Resume Run API through normal FastAPI composition, using the real Resumes-owned durable store and worker with deterministic workspace, provider, spend-authority, PDF, clock, and explicit crash-barrier adapters. Ticket 08 owns route and field names; these tests assert their semantic values.
- Restart tests stop at controlled barriers and construct a fresh application instance over the same run, checkpoint, workspace, PDF, and spend state. They use no timing sleeps. At every pre-seal boundary they prove the Artifact Set ID is unchanged, no provider generation is replayed, no replacement Resume or Note is created, and fresh observed state outranks stale phase evidence.
- One identity test gives multiple candidates in one Resume Run distinct immutable Artifact Set IDs, proves that their evidence cannot overwrite each other, and proves that terminal IDs are never reused. A future run after verified compensation receives a new ID, while the original candidate is never reevaluated.
- A cross-effect crash matrix covers before durable intent, after intent but before dispatch, affirmative non-dispatch, effect applied with response lost, observed evidence recorded, and restart before the next effect. It runs at staging, Resume creation, PDF publication, Note creation, final attachment, logical seal, checkpoint deletion, and every compensation mutation.
- The primary recovery matrix covers every row in `Recovery Classification`: checkpoint/stage only; keyed Resume only; keyed PDF only; keyed Note only; complete set without relation; exact relation; ambiguous creates; missing, altered, archived, duplicated, or invalid pages; missing or corrupt PDF; missing or corrupt checkpoint; partial compensation; independent Resume or source invalidation; quarantine; seal crash windows; and discovered Historical Artifact Drift.
- One focused Notion artifact-store conformance suite runs against both the deterministic workspace and a recorded Notion adapter. It verifies the targeted enhanced-Markdown version and capabilities, required `Merida Artifact ID` properties, complete semantic block round trips, and one `POST /v1/pages` per Resume or Note with no later child append or asynchronous task.
- The Notion conformance seam performs exact-ID lookup in the correct database across complete pagination and counts archived pages. It accepts only one total keyed page that is active and matches properties, expected relations, complete parsed content, and the Artifact Document Digest.
- Ambiguous Resume and Note creation tests distinguish affirmative non-dispatch, one subsequently verified exact match, zero matches, and multiple matches. They also cover archived-only and active-plus-archived results, wrong properties or relations, truncated or unknown content, parse loss, and semantically equivalent normalized Markdown.
- Negative ownership tests explicitly prove that title, company, role, timestamp, filename, similar content, and an independent relation cannot cause adoption, cleanup, attachment, or completion.
- One focused versioned Artifact Document Digest suite publishes golden vectors for ticket 06's chosen serialization. It covers all accepted block kinds, ordered-block sensitivity, separate Resume and Note digests, Unicode NFC, CRLF-to-LF normalization, preserved whitespace/punctuation/case, multibyte text, invalid depth, unknown kinds, truncation, and equivalent enhanced-Markdown formatting.
- Artifact Request Digest tests compare the persisted SHA-256 with the exact enhanced-Markdown bytes dispatched. They keep this wire identity distinct from semantic Artifact Document Digests and returned Markdown formatting.
- One focused PDF artifact-store conformance suite verifies the write-ahead boundary: unowned temporary render, durable document/path/byte evidence, and atomic exposure at the full-ID-addressed staged path. Unowned residue is ignored, evidence without a file permits checkpoint rerender, and a final file without prior matching evidence quarantines.
- PDF tests cover non-overwriting staged and published paths, document and byte digests, valid reuse, deterministic pre-completion rerender, byte or identity mismatch, stale/missing/corrupt index data, lookup reconstruction, and exact-owned removal. Legacy or merely human-named files are never adopted.
- Collision tests complete different roles at one company, repeated pursuits with the same company and role, and normalization-equivalent names. Their internal PDFs coexist, and one Artifact Set cannot overwrite, resolve to, or remove another.
- Completion Gate tests freshly validate the keyed Resume, Note, PDF, stable candidate source, and relation immediately before and after attachment. An absent relation may be attached or repeated; an exact sole relation counts once; a wrong/additional relation, independent Resume, missing artifact, unreconstructable result, or ambiguous source never counts.
- Result reconstruction tests discard cached response objects and restart the app. A completion is reported only from freshly read Resume and Note identities and URLs, the digest-verified PDF lookup and backend route, and the finalized basename; raw filesystem paths, transient URLs, and live source fields are never required.
- One narrow transactional store contract proves that Resume Completion, run progress, terminal seal, compact ownership evidence, and stable result identities commit together or not at all. Concurrent or replayed sealing cannot double-count, while checkpoint deletion remains retryable post-seal cleanup.
- One narrow checkpoint contract proves that the exact private Resume and Note documents and both document digests are atomically bound to the Artifact Set before its first effect. Missing or corrupt required content with remaining effects quarantines and causes zero provider calls.
- Compensation tests inject a lost response and failed readback after every strict reversal step. Failure stops before touching lower effects, restart begins at the first unverified barrier, already-satisfied steps are idempotent, and a sealed completion is never compensated.
- Quarantine tests prove the Application-scoped lock across restart, time passage, lease loss, cancellation, and owning-run completion. They reject generic acknowledgement, allow read-only reconciliation, and exercise the three audited exits without guessing ticket 08's operator transport.
- Independent-artifact tests prove a different active Resume is never adopted, modified, archived, or counted. Unambiguous state affects only the run-owned set; ambiguity quarantines; prior Resume Completions remain untouched.
- Historical-drift tests mutate or remove each sealed Resume, Note, PDF, and relation, then perform supported reads and later run starts. Completion and permanent ownership exclusion remain immutable; no recovery, compensation, replacement, provider call, monitor state, or renewed eligibility occurs.
- Privacy tests inspect public snapshots, errors, normal logs, spend records, recovery inspection, and compact terminal records. They may contain safe IDs, digests, bounded evidence, terminal state, and finalized basename, but not prompts, reasoning, provider payloads, Job Content, Master Resume source, canonical documents, transient URLs, or filesystem paths.
- A separate checkpoint allowlist permits only the exact canonical Resume and Note documents plus minimal binding metadata and proves isolation from public metadata and the content-free spend ledger. Completion or verified compensation removes the checkpoint; post-seal cleanup may delete only checkpoint residue.
- Readiness tests prove that missing or wrong Artifact ID properties, unsupported enhanced-Markdown behavior, incomplete connection capabilities, failed semantic round trip, unavailable durable recovery/checkpoint authority, or unavailable digest-verified PDF storage blocks the Resume Run before provider or artifact work.
- Routine automated tests use deterministic adapters and recordings and make no paid provider or live Notion calls. Sanitized live capability probes are operational readiness evidence rather than ordinary test traffic.
- Durable Application Analysis API/store tests are prior art for public-first durable-run acceptance, fresh-instance restart, explicit barriers, atomic progress, content-free persistence, and safe observation. Resume tests reuse their behavioral shape, not Applications-owned schemas, constants, or outcomes.
- Existing execution-recovery tests are prior art for ambiguous effects, fail-closed recovery data, startup reconciliation, and mutation blocking. Their cleanup-then-fresh-attempt behavior is superseded for a uniquely owned pre-seal Artifact Set by forward Same-Run Artifact Recovery.
- Existing Notion workspace tests are prior art for adapter conformance, unlinked Resume creation, relation-last completion, Note relations, multiple-Resume conflicts, and lost-response compensation. The durable suite replaces the legacy post-create append seam with one enhanced-Markdown create and exact keyed reconciliation.
- Existing PDF export tests are prior art for publish/remove lookup behavior, non-overwrite protection, human naming, and corrupt-index failure. The durable suite replaces company-only identity with full Artifact Set identity and digest-verified write-ahead staging.
- Existing public-contract, Resume generation, and final behavior-inventory tests are prior art for artifact summaries, PDF downloads, canonical Resume/PDF consistency, and protected behavior ownership. The final inventory gains durable ownership, reconciliation, compensation, quarantine, seal, drift, result, and privacy regressions.
