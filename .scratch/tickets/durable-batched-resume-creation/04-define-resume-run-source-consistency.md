# Define Resume Run source consistency and candidate revalidation

Parent: [Wayfinder: Durable Batched Resume Creation](map.md)

Type: grilling

Status: ready-for-agent

State: closed

Assignee: codex

Blocked by: none

## Question

Which Resume Creation inputs are fixed versus reloaded during a Resume Run: when is the Master Resume selected and read, when are each Application's status, Match Score threshold, existing Resume relation, Job Content, and Application Analysis revalidated, and how should mid-run edits, disappearance, or an independently created Resume affect one candidate without changing the fixed Resume Candidate Set or crediting an independent artifact as this run's Resume Completion?

## Decisions

- A Resume Run selects one Master Resume Version at run creation, and every candidate in that run uses that same evidence basis. Master Resume edits made after run creation apply only to later runs; Merida never silently substitutes changed content after a restart or reload. The durability-boundary work will determine whether the private snapshot must be preserved or whether an unavailable matching version blocks recovery.
- Immediately before evaluating a candidate, the run reloads and validates one complete Resume Candidate Source Version. That fixed version supplies Company, Role, the observed Match Score, Job Content, and Application Analysis to Requirements extraction, Draft generation, artifact naming, and rendering. Later source observations may prevent the candidate from continuing, but they never replace individual values or mix revisions within the candidate.
- Resume Candidate Admission occurs immediately before the source version is fixed and before any provider reservation. It requires a readable Application still in `To Apply`, `Analyzed = true`, Match Score at least 70, readable Company, Role, Job Content, and Application Analysis, and no active related Job-Specific Resume. Rejection skips provider and artifact work, consumes the candidate's one evaluation, leaves the fixed Resume Candidate Set unchanged, and allows backfill from the next identity in that set. An independently created Resume causes rejection and never counts as this run's Resume Completion.
- Candidate Admission observes the current Match Score. A changed score of at least 70 becomes the score in that candidate's Resume Candidate Source Version, while a missing or below-threshold score rejects admission. Neither case reorders or replaces identities in the fixed Resume Candidate Set; its run-start Match Score order remains unchanged.
- For a canonical Application Analysis containing a Match Score, Candidate Admission requires that score to equal the current Application Match Score property exactly. A mismatch rejects admission as inconsistent, and the Resumes context neither chooses one value nor repairs Applications-owned analysis data. A readable legacy `Job Posting Analysis` without an embedded score may use the Application property as its sole score authority; that property must still be at least 70.
- A definite change after admission to Company, Role, the accepted Match Score, Job Content, or Application Analysis invalidates the candidate at its next Resume Candidate Continuation Check. The run does not mix in the changed value, continue to artifacts from stale Application evidence, or evaluate that Application again. Earlier provider spend remains committed, the candidate earns no Resume Completion, and the run may backfill from the next fixed candidate. Unrelated Application management fields do not participate. Later Master Resume edits do not invalidate work because the run continues to use its fixed Master Resume Version.
- Resume Candidate Continuation Checks run at Candidate Admission immediately before the first Requirements authorization; immediately before every later provider authorization, including either stage's recovery; and after a validated Draft immediately before PDF staging or any artifact effect. Each check revalidates readability, `To Apply`, `Analyzed`, the Match Score threshold and agreement rule, absence of an independent Resume, and equality of current relevant source values with the admitted Resume Candidate Source Version. Inability to establish safety fails closed; the failure-policy ticket will distinguish definite candidate changes from transient or shared workspace failures.
- A Resume Completion Gate performs one final full Continuation Check immediately before the relation-last commit and verifies the relation afterward. If a different active Job-Specific Resume appears, this run does not adopt it, attach its own Resume beside it, or count a Resume Completion; its run-owned partial artifacts follow ticket 05's compensation or quarantine policy. An already attached exact run-owned Resume may count only from same-run ownership proof. Because Notion offers no conditional relation write, an unresolved race after attachment also cannot count as a Completion.
- A page-level not-found result or definitely missing required source makes the candidate unavailable: no further provider or artifact work occurs, no Resume Completion is earned, any run-owned partial artifacts follow same-run recovery policy, and the run may backfill from the next fixed candidate. A timeout, rate limit, server error, or otherwise ambiguous Notion read is not evidence of disappearance or change; it fails closed without advancing to another candidate. Ticket 07 owns bounded recovery and the eventual run outcome for ambiguous or shared workspace failures.
- Candidate Admission trusts the persisted, internally consistent Applications-owned Match Score and does not recompute or overwrite it against the run's Master Resume Version. Resume Creation separately derives its Resumes-owned Resume Fit Score and evidence gate from that fixed Master Resume Version. Insufficient Resume evidence may reject the candidate and permit backfill without retroactively changing its Application Match Score or fixed Candidate Set position.
- Durable coordination retains Resume Source Version Proof for the run's Master Resume Version and every admitted Resume Candidate Source Version. After restart, no provider or artifact work may continue until the exact dependent versions are proven. Changed Master Resume content never replaces the run's version; if that version cannot be recovered, the run cannot perform further candidate work. Changed Application content never replaces an admitted candidate's version; that candidate is invalidated rather than restarted, while later unadmitted candidates may still capture their own source versions when the fixed Master Resume Version remains available. Ticket 06 chooses fingerprint replay versus any private checkpoint, and ticket 07 names terminal outcomes.
- Master Resume selection, Candidate Admission, and every Continuation Check accept source values only through a Stable Resume Source Observation: identity, relevant properties, complete relations, and selected body content must produce the same canonical observation across bounded verification reads. A moving or torn observation is retried only within later failure policy and otherwise fails closed. This is consistency detection rather than a claim of an atomic Notion snapshot or conditional write; ticket 06 selects timestamps, rereads, relation pagination, and fingerprint mechanics.
- After run creation, editing, archiving, replacing, duplicating, unsharing, or deleting the selected Master Resume page does not revise or implicitly revoke the run when exact Master Resume Version proof remains available. The run continues only from that fixed version and never adopts a replacement; inability to recover it prevents dependent work. Explicit Resume Run cancellation, rather than source mutation, is the operator's stop signal.
- Post-attachment Resume Completion Gate verification obtains another Stable Resume Source Observation rather than checking only the relation. It records a Completion only when all current eligibility and relevant source values still match the admitted Resume Candidate Source Version and the run-owned Resume is the sole active Job-Specific Resume relation. A changed or ambiguous full state does not count and proceeds to ticket 05's same-run recovery, compensation, or quarantine policy.
- Once the Resume Completion Gate succeeds and the run records a Resume Completion, that completion is immutable run history. Later edits, relation changes, archival, or artifact deletion do not decrement progress or reopen the candidate; they are later workspace mutations, and historical repair remains out of scope. Same-Run Artifact Recovery applies only before a Completion has been conclusively recorded.

## Answer

One Resume Run selects one immutable Master Resume Version at creation. Each candidate then consumes one evaluation by passing through fail-closed Resume Candidate Admission, which reloads one Stable Resume Source Observation and fixes one Resume Candidate Source Version before provider spend. The fixed Resume Candidate Set never changes order or membership; current eligibility controls only whether a fixed candidate may proceed.

Every provider authorization, the transition into artifact work, and both sides of the relation-last commit are guarded by source-consistency checks. Relevant Application edits, definite disappearance, threshold failure, score inconsistency, or an independently created Job-Specific Resume prevent further candidate work without replacing source values or crediting an independent artifact. Ambiguous workspace evidence proves no change and cannot advance the run. Restart recovery requires exact Resume Source Version Proof, while a Resume Completion becomes immutable history once its full pre- and post-attachment gate succeeds.

## Problem Statement

An operator-started Resume Run can outlive the Notion records from which it generates Resumes. During that time, the Master Resume or an Application may be edited, archived, replaced, unshared, or removed; an independent Job-Specific Resume may be related; the backend may restart; and Notion may return properties, relations, and body content through separate non-transactional reads. Without an explicit consistency contract, one candidate could mix Master Resume revisions or Application revisions, spend money after its evidence changed, produce artifacts from stale values, silently reorder the fixed Resume Candidate Set, or credit an independent Resume as the run's work.

The operator needs each Resume Run to use one explainable evidence basis, each candidate to receive at most one coherent evaluation, and each Resume Completion to represent a fully verified run-owned result. Source edits must have deterministic effects without pretending Notion offers atomic snapshots or conditional relation writes.

## Solution

At Resume Run creation, Merida selects one Master Resume Version through a Stable Resume Source Observation and fixes the Resume Candidate Set in run-start Match Score order. Every candidate uses that same Master Resume Version.

Immediately before one candidate's evaluation, Resume Candidate Admission obtains a stable current Application observation, revalidates complete eligibility and the absence of an active Job-Specific Resume, and fixes one Resume Candidate Source Version. Fit Requirement extraction, Resume Draft generation, naming, and rendering all use that version. The persisted Applications-owned Match Score controls threshold eligibility without being recomputed by Resume Creation; the Resumes-owned Resume Fit Score remains a separate evidence gate.

Resume Candidate Continuation Checks run before every provider authorization and before artifact work. The Resume Completion Gate repeats the full check before relation-last commit and verifies the complete source, eligibility, ownership, and relation state afterward. Definite source changes or unavailability invalidate only that candidate and may permit bounded backfill. Ambiguous workspace evidence fails closed without consuming later candidates. Recovery continues only from exact Resume Source Version Proof and never substitutes current content. Once the Completion Gate succeeds, the Resume Completion is immutable run history.

## Implementation Decisions

- The Resumes context owns Master Resume Version selection, Resume Candidate Admission, Resume Candidate Source Version establishment, Resume Candidate Continuation Checks, Resume Completion Gates, Resume Source Version Proof requirements, and the separation between Application Match Score and Resume Fit Score.
- Notion remains authoritative for live Applications, the active Master Resume page, and completed Resume artifacts. A Resume Run's fixed source versions are workflow evidence bases; they do not transfer ownership of the underlying product records away from Notion.
- Run creation selects exactly one Master Resume Version through a Stable Resume Source Observation. Every candidate in the run uses it, and later live mutations never alter, revoke, or replace it while exact version proof remains available.
- The Resume Candidate Set remains a fixed run-start snapshot of identities in canonical Match Score order. Revalidation never inserts, removes, or reorders identities. Beginning Resume Candidate Admission consumes that identity's single evaluation even when admission rejects it.
- Resume Candidate Admission occurs immediately before the first Requirements authorization and before any provider reservation or artifact effect. It establishes one Resume Candidate Source Version only after a complete fail-closed eligibility check succeeds.
- Admission requires a readable Application in `To Apply`, `Analyzed = true`, a persisted Match Score of at least 70, readable Company, Role, Job Content, and Application Analysis, internally consistent Match Score evidence, and no active related Job-Specific Resume.
- An admission rejection makes no provider reservation, dispatch, PDF, Resume, Note, or relation mutation. It earns no Resume Completion, leaves the fixed Resume Candidate Set unchanged, and may permit backfill from the next fixed identity.
- The Resume Candidate Source Version fixes Company, Role, the accepted Match Score observation, Job Content, and Application Analysis for Requirements extraction, Resume Draft generation, artifact naming, and rendering. Later observations may veto work but never replace individual source fields.
- Candidate Admission uses the current Match Score for threshold eligibility. An above-threshold change becomes the candidate version's accepted score without changing the fixed Candidate Set order; a missing or below-threshold score rejects admission.
- A canonical Application Analysis with an embedded Match Score must agree exactly with the Application Match Score property. A mismatch rejects admission without choosing, recomputing, or repairing either Applications-owned value. A readable legacy `Job Posting Analysis` without an embedded score may use the property as sole authority when it remains at least 70.
- Resume Creation never recomputes or overwrites the Applications-owned Match Score against the run's Master Resume Version. The Resumes-owned Resume Fit Score and evidence gate are calculated separately; insufficient Resume evidence can reject a candidate without changing Application Analysis history.
- Master Resume selection, Candidate Admission, every Continuation Check, and both Completion Gate observations require a Stable Resume Source Observation. A canonical observation covers identity, relevant properties, complete paginated relations, and selected body content and is accepted only when bounded verification observations agree.
- A Stable Resume Source Observation detects consistency but does not claim an atomic Notion snapshot. The workspace interface must expose complete observations and distinguish stable values, definite unavailability or invalidity, and ambiguous provider failure. Exact canonicalization, fingerprints, reread bounds, timestamps, and transport mechanics belong to the durability prototype.
- Resume Candidate Continuation Checks occur before the first Requirements authorization, before every later provider authorization including either stage's recovery, and after a validated Draft immediately before PDF staging or any artifact effect.
- Every Continuation Check revalidates readability, `To Apply`, `Analyzed`, Match Score threshold and agreement, absence of an independent active Job-Specific Resume, and equality of current Company, Role, accepted Match Score, Job Content, and Application Analysis with the admitted Resume Candidate Source Version.
- A definite relevant source change, eligibility loss, existing Resume, page-level unavailability, or missing required source invalidates that candidate. No later provider or artifact action occurs, already committed provider spend remains committed, no Completion is earned, the candidate is never reevaluated within the run, and bounded backfill may continue.
- Changes to unrelated management fields do not invalidate a candidate. Later live Master Resume mutations also do not invalidate it while the fixed Master Resume Version remains provable.
- An ambiguous timeout, rate limit, server error, incomplete observation, or moving/torn read is not evidence of source change or disappearance. Work fails closed without advancing to another candidate; retry limits, failure scope, reason codes, and eventual run outcomes belong to the failure-policy ticket.
- An independently created Job-Specific Resume never becomes part of the run's artifact set and never counts toward the Resume Batch Target. Discovery before admission rejects the candidate; discovery later prevents further work or Completion according to the same continuation and gate rules.
- The Resume Completion Gate performs a full Continuation Check immediately before the relation-last commit. A different active Resume prevents adoption and parallel attachment. An exact already-attached run-owned Resume is recoverable only through independently established same-run ownership proof.
- Because Notion does not provide a caller-controlled conditional relation write, the Completion Gate performs a second Stable Resume Source Observation after attachment. Completion requires the full current eligibility and relevant source values to equal the admitted version and the exact run-owned Resume to be the sole active Job-Specific Resume relation.
- A changed, conflicting, unavailable, torn, or ambiguous post-attachment observation records no Completion. Run-owned partial artifacts pass to the separately defined Same-Run Artifact Recovery, compensation, or quarantine policy; source consistency never guesses artifact ownership or effect outcomes.
- Resume Source Version Proof is required after restart before dependent provider or artifact work. Exact selected content may be replayed, but current content never substitutes for a fixed version. An admitted candidate whose live source changed is invalidated rather than restarted; later unadmitted candidates may establish their own source versions when the fixed Master Resume Version remains available.
- The durability prototype decides whether exact source proof uses content-free fingerprints plus replay, a private checkpoint, or operator blocking. It also owns physical storage, transaction boundaries, lease behavior, and crash recovery. This spec fixes only the semantic requirement that substitution is forbidden.
- Once the Resume Completion Gate succeeds, the Resume Completion is immutable historical run progress. Later Application, relation, Master Resume, Resume, Note, or PDF mutations neither decrement the run nor reopen the candidate. Historical artifact repair remains outside this workflow.
- Provider transmissions and reservations continue to obey the accepted Resume Generation Envelope and Resume Run Spend Ceiling. Source invalidation never releases verified or indeterminate spend, restores a consumed dispatch slot, changes models, or lowers quality.
- No public route names, response field names, candidate reason codes, lifecycle states, or terminal outcome names are fixed here. Later public-contract and failure-policy work will expose this behavior without returning private source content or internal proof material.

## Testing Decisions

- Tests assert externally observable Resume Run progress, candidate evaluation behavior, provider reservations and dispatches, Notion-visible source and relation state, artifact boundaries, and restart results. They do not assert helper names, physical run-store tables, a particular source-proof representation, worker polling cadence, or the fingerprint and reread mechanics reserved for the durability prototype.
- The primary acceptance seam is the eventual public Resume Run API through normal FastAPI composition. It uses the real Resumes-owned durable run store and worker with deterministic workspace, provider, spend-authority, artifact, clock, and explicit barrier adapters. The seam observes safe run snapshots, reservations and dispatches, and workspace-visible results.
- Restart tests construct a fresh application instance over the same durable run, spend, artifact, and workspace state. Mutation and concurrency tests use explicit barriers at admission, provider authorization, validated Draft, artifact, and relation boundaries rather than sleeps.
- One narrower source-observation conformance seam runs against both the deterministic workspace and recorded Notion adapter. It proves complete paginated relations and canonical observations across split property/body reads, accepts identical bounded observations, and fails closed for moving, torn, incomplete, or ambiguously failed observations. It asserts domain observations and classifications rather than HTTP call counts or one fingerprint algorithm.
- Fixed-source consumption is verified at the primary seam with safe prepared-request fingerprints and observable artifact outputs. Requirements, Draft generation, naming, and rendering must all derive from the admitted Resume Candidate Source Version and fixed Master Resume Version without exposing private source content in public progress.
- The primary seam covers a fixed run-start Candidate Set and Master Resume Version; later queue mutations and above-threshold score changes cannot change identities or order, while a later run may select a newer Master Resume Version.
- Admission tests cover success plus status loss, `Analyzed = false`, missing or below-threshold score, missing required source, canonical score mismatch, definite page unavailability, and an independent Resume. Every rejection consumes one evaluation but causes no reservation, dispatch, artifact effect, or Completion and may backfill only from the fixed set.
- Score tests cover above-threshold admission without reordering, exact canonical body/property agreement, the legacy no-embedded-score exception, no Match Score recomputation against the run's Master Resume Version, and separate Resume Fit rejection without Applications-owned mutation.
- A continuation-boundary matrix injects each relevant source or eligibility change before Requirements recovery, initial Draft, Draft recovery, pre-artifact work, and the pre-relation Completion Gate. No next paid or artifact action may occur; old and new source values are never mixed; earlier spend remains committed; and the candidate is not evaluated again.
- Non-participating-change tests edit only unrelated Application management fields or the live Master Resume while exact fixed-version proof remains available and verify that work continues from the admitted versions.
- Ambiguity tests inject timeouts, rate limits, server failures, incomplete relation pagination, and moving/torn observations at Master selection, Admission, every Continuation Check, and both sides of relation attachment. No unsafe source selection, authorization, artifact effect, Completion, or advance to another candidate may occur.
- Complete-relation tests place an independent active Resume outside the first relation page and verify that Admission and the Completion Gate still detect it.
- Restart tests cover restart after run creation but before admission, after admission but before a later provider call, and after a validated Draft but before artifacts. Exact provable versions continue without substitution; an unavailable Master version prevents dependent work; a changed admitted Application invalidates that candidate; and a later unadmitted fixed candidate may capture a current version only when the run's Master version remains provable.
- Pre-attachment Completion Gate tests verify a final full stable check before relation mutation. Source change, eligibility loss, independent Resume, definite unavailability, or ambiguity prevents attachment and Completion and hands identifiable partial artifacts to the ticket 05 policy.
- Post-attachment Completion Gate tests count a Completion only after a stable full observation proves source equality, current eligibility, exact same-run ownership, and the sole active Resume relation. Changed or ambiguous state, a different or additional Resume, or source disappearance cannot count.
- Immutable-history tests mutate Application source, relations, Master Resume, Resume, Note, or PDF after a conclusively recorded Completion and verify that progress never decrements, the candidate never reopens, and Same-Run Artifact Recovery is not invoked for the historical mutation.
- Durable Application Analysis run tests are prior art for fixed candidate snapshots, revalidation, backfill, restart through fresh application composition, explicit provider barriers, and public run observation. ## Further Notes

- Current synchronous Resume Creation performs multiple live Application reads, loads the Master Resume per create, checks the existing Resume relation only before generation, and performs no later source revalidation. It also accepts any non-null Match Score instead of enforcing the canonical 70-percent Resume Match Threshold. Those are current-state gaps, not accepted semantics.
- Notion exposes useful edit metadata but no documented caller-controlled conditional update for the final relation. Application properties, relations, and body blocks are separate observations, and relation values can require pagination. Stable Resume Source Observation therefore means bounded consistency detection, not atomic isolation.
- The source-consistency policy deliberately spends extra workspace reads to prevent further provider or artifact work after relevant edits. The durability prototype should measure and minimize those reads without weakening the accepted boundaries.
- Ticket 05 owns run-owned artifact identity and Same-Run Artifact Recovery. Ticket 06 must prove the smallest privacy-safe durability design that can satisfy Resume Source Version Proof. Ticket 07 converts definite and ambiguous conditions into failure scopes, retry policy, reason codes, and terminal outcomes. Tickets 08 and 09 expose and present only the safe resulting contract.
- No ADR is added by this ticket. The fixed-source behavior is an explicit workflow policy; any surprising, hard-to-reverse storage or integration trade-off revealed by the durability prototype should be evaluated separately for an ADR.
